如果我是 Android 这边负责人，我会采用 “先找最小差异，再决定是否移植 xone” 的路线，而不是马上把整个 xone 塞进 BSP。

我的推荐结论

分两阶段：

1. 先在 Ubuntu 上把成功的 xone 会话与失败的 xpad 会话做 A/B 差分
2. 根据差分结果选择：
  • 差异很小：给 Android xpad.c 加最小补丁
  • 确实依赖完整 GIP 状态机：移植 xone 的“有线手柄最小子集”

这样最快，也最稳。

第一阶段：找出真正必要的最小步骤

目前同时变化的东西太多：

• 初始化握手
• identify
• authentication
• ACK/chunk
• stop-rumble 初始化
• rumble 强度映射
• repeat 字段
• 发送间隔
• client ID / sequence

所以虽然 xone 已经震了，我们还不能断言必须移植全部代码。

→ ACK
→ identify
→ authentication
→ power-on
→ stop-rumble
→ 5次正式震动

然后把所有 OUT 包按时间整理出来。

第二步：按性价比逐项测试

我会依次验证：

实验 A：只改 rumble payload

motors = 0x0f
left   = 0x7f
repeat = 0xff

xone 发的更接近：

motors = 0x0f
left   = 0x64
repeat = 0xeb

先保持旧 xpad 会话，只改成 xone 的字段和10ms发送间隔。

如果震了，Android 只需改十几行。

实验 B：先发 stop-rumble 初始化

xone 在注册 FF 时会先发：

四马达 mask
所有强度为0
duration = 0xff
repeat   = 0xeb

然后才允许正式震动。

如果给 xpad 补这一条后就能震，Android 补丁同样很小。

实验 C：补 identify / ACK

如果前两个不行，再让 xpad：

announce
→ 正确 ACK
→ identify
→ 完成 chunk
→ stop-rumble
→ 正式 rumble

实验 D：验证 authentication 是否必要

最后再判断认证。

如果不完成认证仍能震，就不必移植 xone 的 crypto/auth；如果只有认证完成后才震，才进入完整移植路线。

第二阶段 A：最理想——只补 Android xpad

如果上述实验找到最小组合，例如：

正确 ACK + identify + stop-rumble + repeat=0xeb

我会直接修改 Android 的：

kernel_platform/msm-kernel/drivers/input/joystick/xpad.c

可能涉及：

1. 处理 0x03 announce/status
2. 回 0x01 ACKNOWLEDGE
3. 请求 0x04 identify
4. 完整处理 chunk
5. 初始化时发送 stop-rumble
6. 改 Wolverine 的 rumble 参数和时序

同时只对：

• 改动小

这是我最希望得到的结果。

四、xone 发的震动包有什么不同？

xone 的 rumble payload 是：

struct gip_gamepad_pkt_rumble {
    u8 unknown;
    u8 motors;
    u8 left_trigger;
    u8 right_trigger;
    u8 left;
    u8 right;
    u8 duration;
    u8 delay;
    u8 repeat;
};

满强度测试时，xone 使用的主要字段大致是：

unknown       = 00
motors        = 0f
left_trigger  = 00
right_trigger = 00
left          = 64    // 十进制100
right         = 00
duration      = ff
delay         = 00
repeat        = eb

旧 xpad 则发：

left   = 7f
repeat = ff

也就是说两者至少存在这些差异：

• xpad 满强度映射到 0x7f
• xone 满强度映射到 0x64
• xpad 的 repeat 是 0xff
• xone 的 repeat 是 0xeb
• xone 对连续 rumble 之间强制保留至少约10ms间隔
• xone 在注册 FF 时会先发送一条“停止震动初始化包”

其中 xone 源码对最后一点有明确注释：

stop rumble
(required for some exotic gamepads to start input)

意思是某些特殊手柄必须先收到一条合法的“全马达停止”命令，才会进入正常输入/震动状态。

Wolverine 很可能正属于这种对初始化状态比较挑剔的设备。

五、完整会话和认证是不是决定因素？

可能是，但现在不能说已经唯一确定。

xone 做了旧 xpad 没做完整的事情：

设备 announce
→ 主机 ACK
→ 请求 identify
→ 设备返回能力和接口
→ 建立 gamepad client
→ power-on
→ 启动 authentication
→ 发送 stop-rumble 初始化
→ 正式 rumble

旧 xpad 主要是：

识别成 Xbox One
→ 发通用 power/init
→ 直接接受输入
→ 直接发 rumble

不过，从 xone 源码来看，authentication 是异步进行的，input 设备不一定要等整套认证彻底结束才注册。因此目前最严谨的说法是：

xone 建立了比 xpad 完整得多的 GIP 会话；其中 identify/client 状态、stop-rumble 初始化、字段差异和发送时序，至少有一项是 Wolverine 接受震动的必要条件。

不是简单一句“认证成功所以震了”就能完全解释。

    u8 delay;
    u8 repeat;
};

满强度测试时，xone 使用的主要字段大致是：

unknown       = 00
motors        = 0f
left_trigger  = 00
right_trigger = 00
left          = 64    // 十进制100
right         = 00
duration      = ff
delay         = 00
repeat        = eb

旧 xpad 则发：

left   = 7f
repeat = ff

也就是说两者至少存在这些差异：

• xpad 满强度映射到 0x7f
• xone 满强度映射到 0x64
• xpad 的 repeat 是 0xff
• xone 的 repeat 是 0xeb
• xone 对连续 rumble 之间强制保留至少约10ms间隔
• xone 在注册 FF 时会先发送一条“停止震动初始化包”

其中 xone 源码对最后一点有明确注释：

stop rumble
(required for some exotic gamepads to start input)

意思是某些特殊手柄必须先收到一条合法的“全马达停止”命令，才会进入正常输入/震动状态。

Wolverine 很可能正属于这种对初始化状态比较挑剔的设备。

───

五、完整会话和认证是不是决定因素？

可能是，但现在不能说已经唯一确定。

xone 做了旧 xpad 没做完整的事情：

设备 announce
→ 主机 ACK
→ 请求 identify
→ 设备返回能力和接口
→ 建立 gamepad client
→ power-on
→ 启动 authentication
→ 发送 stop-rumble 初始化
→ 正式 rumble

旧 xpad 主要是：

识别成 Xbox One
→ 发通用 power/init
→ 直接接受输入
→ 直接发 rumble

不过，从 xone 源码来看，authentication 是异步进行的，input 设备不一定要等整套认证彻底结束才注册。因此目前最严谨的说法是：

xone 建立了比 xpad 完整得多的 GIP 会话；其中 identify/client 状态、stop-rumble 初始化、字段差异和发送时序，至少有一项是 Wolverine 接受震动的必要条件。

不是简单一句“认证成功所以震了”就能完全解释。

───

六、为什么 Android 那边搞了那么久？

因为当时掌握的证据很容易把人带进错误方向。

1. 所有 Linux API 都返回成功

通常遇到：

EVIOCSFF成功
EV_FF成功
URB成功

会自然认为协议只差一个字段，导致我们不断调整：

• 马达强度；
• motor mask；
• 重发频率；


哈哈，聪明有一点，但真正关键的是没有继续硬猜包，而是找到了更完整的开源实现，并用实机证据把它跑通。🦞

为什么旧 xpad 不震？

旧 xpad 对 Xbox/GIP 的支持比较简化：

发一个通用启动包
→ 直接发13字节 rumble

USB 虽然返回成功，但这只代表：

“数据已经送到手柄。”

不代表：

“手柄已完成合法会话并接受震动命令。”

因此它就像门卫收到了命令纸条，但你还没完成登记，门卫不执行。

为什么 xone 能震？

我改用了 medusalix/xone 的完整 GIP 实现，它先完成：

设备 announce
→ 主机 ACK
→ identify
→ 解析设备能力
→ authentication
→ power-on
→ 建立 gamepad client
→ 发送 stop-rumble 初始化
→ 再发送正式 rumble

完成这些之后，手柄才把后面的13字节震动包当成有效命令。

还有一个很可能关键的细节：xone 注册手柄时会先发送一个停止震动初始化包，注释明确说部分特殊手柄必须收到它，输入和震动才能正常开始。旧 xpad 没做完整这一套。

所以真正根因

不是：

• 马达坏了；
• Android FF API 坏了；
• 0a3f 天生不能震；
• USB 包发送失败。

而是：

旧 xpad 缺少 Wolverine 所需的完整 GIP 会话状态机；xone 把这套流程补齐了。

这次我们已经实机证明：

• 0a3f Xbox 模式输入正常；
• 完整 GIP 驱动成功识别；
• FF 能力正常；
• 连续多轮5次脉冲均物理震动。
