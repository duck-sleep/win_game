## 0. 三句话版本

1. **公网方案 = 让你在外面（公司、路上、别人电脑上）也能看到家里板子的画面并操作它。**
2. **码流不走云。** 云只负责告诉双方"彼此的地址在哪"（相当于电话接线员，只牵线，不听内容）。
3. 能落地的就两条路：**Tailscale**（不装服务器、但每台设备要装 App）／ **JetKVM 那套云**
   （不用装 App、任何浏览器打开网址就行，但要有一台公网机器帮忙转发信令）。

## 1. 名词小抄（读图时随时回来查）

| 名词 | 说人话 |
|---|---|
| **公网 IP** | 全世界都能找到的门牌号。家里宽带一般**没有**，只有运营商给路由器一个共享地址 |
| **NAT** | 小区门卫：里面几十台设备共用一个对外地址，**只出不进**（外面主动敲门会被丢掉） |
| **端口映射** | 拜托门卫："外面敲 8001 号门请转给 192.168.31.89"。前提是**有公网门牌号**，且路由器能设 |
| **内网穿透** | 不打洞也不求门卫，**从家里主动往外连一条常开的线**，外面的人顺着这条线把消息带回来 |
| **信令** | 打电话前的"接线员"：告诉双方彼此的地址、用什么端口、用什么编码。**信令不通，后面全不通** |
| **ICE / 候选地址** | WebRTC 自报家门的清单：`host`=内网地址、`srflx`=打洞后别人看到的地址、`relay`=走中继的地址 |
| **STUN** | 只会回答"我看你的来源地址是 X"的小服务器 ⇒ **只告诉你门牌号，不转发数据** |
| **TURN** | **中继站**：两边实在连不上，就把数据都交给它转发。一定能通，但多一跳、要花钱/额度 |
| **隧道 / WireGuard** | 两台机器之间封一条加密管道，各自得到"虚拟网内地址"（Tailscale 是 `100.x.y.z`），互相看成同一局域网 |
| **tailnet** | 你自己那组装了 Tailscale 的设备组成的私有网络，一个账号管所有 |
| **OIDC / Google 登录** | 一种"让 Google 替你证明你是谁"的标准流程。**证明的是"谁"，不传输任何画面** |
| **id token** | Google 签发的**一段带签名的身份证明**，里面写着"这个人是 xxx@gmail.com、唯一 ID 是多少"。谁都能解出内容，但**谁也伪造不了签名** |

## 3. 为什么"出门就连不上"（两处同时卡死）

```
【现在只有局域网这条路】
  手机/电脑（浏览器）  ──① 信令 HTTP :8001──►  板子 192.168.31.89
                     ◄─② 画面+控制 WebRTC（UDP）
  中间只有家里路由器：不转发任何端口、没有公网入口
```

1. **信令地址不可路由**：`192.168.31.89` 在蜂窝网上根本不存在，连"我要连你"这句话都发不出去；
2. **ICE 只有局域网地址**：我们建 PeerConnection 时用的是空配置
   （[`board/gw/main.go:117`](../../26_k11c_kvm/board/gw/main.go) `webrtc.Configuration{}`），
   没 STUN 也没 TURN ⇒ 就算信令通了，双方也只知道彼此的内网地址，握不上手。

> 顺带一个让人安心的事实：**JetKVM 的"局域网模式"和我们这版行为完全一样**
> （他 `web.go:202` 那个入口，`isCloud=false` 时不填任何 ICE 服务器）。
> 我们不是"做了个残缺版"，是**正好等于他的 LAN 档**。

## 4. JetKVM 的公网方案：九步

**核心思路一句话：不做穿透。让设备永远只往外连，一个入站连接都不接。**
洞是设备自己挖的 ⇒ 家里路由器什么都不用设。

```
                    ☁ 公网 api.jetkvm.com（他自己也挂在 Cloudflare 后面）
                    存三样东西：
                      activeConnections = deviceId → { 长连接, 云端看到的设备公网IP, 版本 }
                      inFlight          = 此刻正在看这台设备的观看者（只放 1 个）
                      TURN 凭据          = 现场找 Cloudflare 托管 TURN 领（只发给浏览器）
                    ▲                                          ▲
                    │ ② 设备开机就拨一条 WS，一路挂着不断         │ ⑤ 观看者浏览器的 WS（带 Google 身份）
                    │    Authorization: Bearer <长期令牌>         │
               ┌────┴──────────────┐                   ┌─────────┴───────────┐
               │ 板子：在家里        │                   │ 浏览器：在外面        │
               │ 无公网IP、无端口映射 │                   │ app.jetkvm.com       │
               └────┬──────────────┘                   └─────────┬───────────┘
                    │                                            │
                    └─────── ⑨ 媒体：WebRTC UDP，**不经过云** ─────┘
                               直连成功 → P2P（最快）
                               直连失败 → 走 Cloudflare TURN 中继兜底
```

**九步细看**（括号里是他源码位置）：

1. **配对**：App 出一个配对码 → 设备拿它换**长期令牌**（`cloud.go:226` `POST {cloud}/devices/token`）。
2. **设备挂上去**：带 `Authorization: Bearer <令牌>` 主动拨 WebSocket 到云（`cloud.go:327-342`），
   头里报 `X-Device-ID / X-App-Version / X-Device-SKU`。
3. **云顺手记下设备的公网地址**：`ip = REAL_IP_HEADER || socket.remoteAddress`
   （`webrtc-signaling.ts:156-158`）——云天然看得见是谁给它发包。
4. **心跳**：云每 10 秒 ping 一次，两次不回就断开（`webrtc-signaling.ts:181-191`）。
5. **观看者到场**：浏览器带 Google 登录态连 `/webrtc/signaling/client?id=<设备>`，
   云查库确认"这台设备的主人就是你"才放行；已经有别人在看就拒掉后来者（`inFlight`）。
6. **信令加料**：浏览器的 offer 经过云时被塞进三样东西再发给设备（`webrtc-signaling.ts:337-349`）：
   真正的 SDP、**设备自己的公网 IP**、给设备的 **STUN 清单**（只有 STUN，没有 TURN）。
7. **设备验身份**：验 `OidcGoogle` 那段 token，且必须等于设备绑定的主人，否则直接拒绝（`cloud.go:400-426`）。
8. **设备组装 ICE**：把第 6 步收到的 `ip` **当成自己的一条公网候选**
   （`SetICEAddressRewriteRules{Append, AsCandidateType: srflx}`，`webrtc.go:461-475`）
   ——**连 STUN 查询都省了**，因为云已经告诉它答案。
9. **媒体怎么走**：优先 P2P 直连；打洞失败才靠浏览器侧的 TURN 中继
   （凭据是浏览器单独领的，`ttl:3600`，云上按用户记转发了多少字节 = 他的成本账）。

> 为什么第 8 步能成立：云看见的就是设备"出站"用的那个地址，NAT 对"自己先发过包"的回程是放行的。
> 前提是 NAT 端口保持（锥形）；对称 NAT 下这条候选无效，得靠 TURN 兜底。

## 5. 🔑 Google 登录到底在干什么（你问的"设备认证"是啥）

### 5.1 一句话

**那一步不是"登录 KVM"，是"把你的 Google 账号和这台设备绑在一起"。**
绑完之后，云才知道"这台设备只允许谁来看"，设备也才知道"我该相信谁的连接请求"。

### 5.2 谁在跟谁说话（实际抓到的流程）

```
你（浏览器）               我们的板子                JetKVM 的云                   Google
     │                        │                        │                            │
     │ 1. 打开板子上的注册页   │                        │                            │
     │───────────────────────►│                        │                            │
     │ 2. 页面里是个表单：POST deviceId + returnTo（回跳地址）                        │
     │────────────────────────────────────────────────►│                            │
     │ 3. 云说：去 Google 验一下（302，带它自己的 client_id）                        │
     │◄────────────────────────────────────────────────│                            │
     │ 4. 你在 Google 登录 + 同意"把身份交给这个应用"                                  │
     │─────────────────────────────────────────────────────────────────────────────►│
     │ 5. Google 回跳：api.jetkvm.com/oidc/callback?code=…（带你的身份签名）          │
     │◄─────────────────────────────────────────────────────────────────────────────│
     │ 6. 云验签 → 在数据库里"认领"这台设备（deviceId 属于你），生成 5 分钟有效的临时令牌
     │                        │                        │                            │
     │ 7. 云把你送回板子的 /adopt?tempToken=…&oidcGoogle=…（回跳地址是第 2 步我们给的）│
     │───────────────────────►│                        │                            │
     │                        │ 8. 板子拿 tempToken 换长期令牌 secretToken（40 位）    │
     │                        │───────────────────────►│                            │
     │ 9. 板子从此用 secretToken 拨 WS，挂在云上                                       │
```

**关键点**：第 7 步的回跳地址（`returnTo`）**是设备自己给的**，所以临时令牌会回到**设备本地**，
只有设备能拿到 ⇒ 令牌不会经过我们这些中间人。

### 5.3 手机上弹的"设备认证 / 是不是你在登录"是什么

那不是 KVM 的东西，是 **Google 账号自己的安全确认**。触发条件：你在一个"没见过的浏览器/设备"
上用 Google 账号授权，Google 会额外确认一次（常见形式：手机收到一条"是否是你本人登录"的提示、
或者要求输一次验证码）。**它防的是别人拿你的账号乱授权，跟 KVM 本身没关系。**

另外还有一层**他自己的"设备归属"**：第 6 步云把 `deviceId` 绑到你的 Google 唯一 ID 上。
绑过之后再有人用别的账号来认领同一台设备，云会直接跳 `/already-adopted`（`oidc.ts:127-139`）。
所以"这台 KVM 属于谁"是靠 **Google 账号**记的，不是靠设备上的密码。

### 5.4 为什么"必须同一个浏览器完成"

云的会话 cookie 设了 `samesite=strict`（`index.ts` 里 `cookieSession` 配置）。
换成"用 A 浏览器点开始、B 浏览器完成登录"，那串 cookie 就丢了，云在回调时找不到"刚才那次请求"，
直接报 `Missing CSRF in session`。**这不是 bug，是防跨站伪造的机制。**

### 5.5 为什么设备还要自己再验一次

这是 JetKVM 讲的"零信任"：**设备不信任云**。云把观看者的 `OidcGoogle`（Google 签名的那段身份）
原样转给设备，设备**自己**用 Google 的公钥验签名，再跟自己绑定的主人比对。
所以就算云被攻破，设备也不会让陌生人来按键盘。

## 6. 我们实测的那一遍（10-29 夜，从零到出画面）

### 6.1 实际跑起来的样子

```
 浏览器                      api.jetkvm.com              板子
   │                              │                        │
   │ ①Google 登录 → tempToken     │                        │
   │                              │◄──②tempToken 换 secretToken（40 位）
   │                              │◄──③拨 WSS（Bearer + X-Device-ID/SKU）→ 在线
   │ ④打开 app.jetkvm.com 里的设备 │                        │
   │──────⑤ offer（base64 的 SDP）────────────────────────►│
   │                              │                        │ ⑥pion 按 H.265 pt=49 应答
   │◄─────⑦ answer + 候选 ────────│◄───────────────────────│
   │◄═════════ ⑧ H.265 60fps 码流（WebRTC UDP，不经过云）══│
   │═════════ ⑨ 四条 datachannel：rpc / hidrpc / hidrpc-unreliable-* ═════►│
```

### 6.2 抓到的报文长什么样（简化）

```jsonc
// 云端推给设备的 offer（我们实际收到的，10501 字节）
{
  "type": "offer",
  "data": {
    "sd": "eyJ0eXBlIjoib2ZmZXIiLCJzZHAiOiJ2PTBcclxu..."  // base64( {"type":"offer","sdp":"..."} )
    "ip": "183.23.146.74",                                 // 云端看到的「我们设备」的公网地址
    "iceServers": ["stun:stun.cloudflare.com:3478"],        // 只给 STUN，没给 TURN
    "OidcGoogle": "eyJhbGciOiJSUzI1NiIs..."                 // 观看者的 Google 身份（设备要自己验）
  }
}
```

**我们发回去的 answer** 也是同样包装：`base64( {"type":"answer","sdp":"…"} )`。
设备侧的 H.265 载荷类型、STUN 服务器、srflx 改写规则，全都是按上面三个字段动态决定的 —— **没有写死的云地址**。

### 6.3 结果与数字（口径都写清）

| 项 | 实测 |
|---|---|
| 注册 | ✅ 换到 40 位 `secretToken` |
| 上线 | ✅ `wss://api.jetkvm.com/` 握手成功（云端认了这台设备） |
| 建连 | ✅ **ICE 1 秒内 connected**，走 STUN 打洞，**没用到中继** |
| 视频 | ✅ 协商到 **H.265 pt=49**，60fps 持续推流 |
| 控制 | ✅ 四条通道建立；hidrpc 握手回显后，鼠标/键盘报文转成 JSON-RPC 打到本机 `:8000` → USB HID |
| 延迟 | 手机（云页面）比电视慢 **33 ms（2 帧）** |

⚠️ **这个 33 ms 的口径要说明**：当时手机连的是**家里同一个 WiFi**，ICE 会优先选局域网地址 ⇒
媒体根本没出家门。所以它证明的是"云端信令 + 前端兼容没问题"，**不代表公网延迟**。
要测公网：**手机关 WiFi 走蜂窝**，再拍一张电视+手机同框照（看两边的毫秒码表差）。

## 7. 路线怎么选

### 7.1 三条路线对照

| 路线 | 要不要装东西 | 要不要公网服务器 | 我们要改多少 | 适合谁 |
|---|---|---|---|---|
| **A. Tailscale** | 板子 + 每台要用的设备都要装 | 不用 | **零**（pion 会把 tailscale 网卡当合法候选） | 自己用、能接受装 App |
| **B. JetKVM 那套云** | **不用装**，任何浏览器打开网址就行 | 要（或用他现成的） | 小：网关/页面各一处 `iceServers` + 一个云客户端 | 要"给谁都能看"的产品形态 |
| **C. cloudflared 隧道 + Cloudflare TURN** | 不用装 | 不用买 VPS | 同 B | 不想买服务器，但**国内可达性未证** |
| D. 路由器端口映射 | 不用装 | 不用 | 要给 pion 框死 UDP 端口范围 | ⚠️ 前提未验（运营商是否 CGNAT）；**没认证前不许** |
| E. 只穿 HTTP（frp/隧道） | — | — | — | ❌ 带不动 WebRTC 的 UDP 媒体，只能退回 MJPEG，**不算方案** |

### 7.2 那"能不能直接用他的云"？

分三层说（都是查代码得到的，不是猜）：

1. **技术上能不能被注册进去？能。** 云端对 `deviceId` 是任意字符串
   （`oidc.ts:146-157` 直接 `create: { id: deviceId }`），不验硬件。
2. **设备号要不要伪造？不用。** 他的 `GetDeviceID()` 读的是通用 `/proc/cpuinfo` 里的 `Serial :`，
   我们板子有真号 `598b4eba996bfdf6`（RK3566 OTP）——**开箱即用**。
3. **🔴 但有一条红线：SKU 绝不能填 `jetkvm-v2`。** 他 `skus.ts` 里那个 SKU 的更新包是
   **RV1106 的 `system/update.img`**，前端一看"设备在线"就可能弹更新，刷进 RK3566 = 废板。
   填**未知 SKU**（我们用 `k11c-rk3566`）反而安全：连接照常，取固件接口直接 400，刷不进去。

**所以"能不能用"剩下的不是技术问题，是三件要谈的事**：
① 一个正式的 SKU 名（让对方内部加一行，避免更新接口 400）；
② TURN 额度（云上按用户统计转发字节，那是他在付钱；官方文档也写明 STUN/TURN 是 Cloudflare 免费提供的）；
③ 前端对"未知 SKU/非 JetKVM 设备"的表现，要不要对方加白。

### 7.3 各路线具体要做什么

* **A. Tailscale**：注册一个账号（Google/GitHub 登录即可）→ 板子装一个包 → 手机装 App → 两边勾同一账号。
  代价：每台要用的设备都得装；手机会变"全局 VPN"。
* **B/C**：按第 4 节的九步，把信令入口（云或隧道）和 ICE 服务器（Cloudflare TURN）接上；
  网关和页面各填一处 `iceServers`，再跑一个云客户端。
* **D**：先验运营商给的是不是真公网 IPv4（WAN 口落在 `100.64.x`/`10.x`/`172.16-31.x` 就是 CGNAT，白做）。

## 8. 还差什么

**软件侧（不需要新硬件，可以马上做）**

1. **认证**——现在 `:8000` 零鉴权，谁能连上谁就能注键盘鼠标（HID 注入 = 拿到被控机完全控制权）；

## 9. 自己搭一套：从零到"公网能看、能控"

> **先说结论**：最难的一半我们已经跑通了 —— 板子上的 pion 能接住标准 offer、能打洞出画、能收键鼠。
> 缺的是**云的那一半**：一个出站 WS 接入点、一个把浏览器的 offer 转给设备的接口、一对 ICE 服务器、一个登录入口。
> 所以下面六步里，**只有第 3 步要改板子**，其余五步全在一台服务器上。
>
> 标注沿用前面：【已证】= 我们在板子上真跑过；【未证】= 还没测，别当真。

### 9.0 动手前先拍三个板

| 要拍的事 | 选项 | 建议 | 为什么 |
|---|---|---|---|
| **服务器放哪** | 大陆云 / 香港·新加坡 | **先香港轻量** | 大陆要 ICP 备案（域名实名 + 网站内容审核），个人项目周期长；香港免备案，深圳过去 RTT 大约 30~60 ms，够用。缺点：跨境线路晚高峰会抖，抖动多少【未证】 |
| **谁证明"你是主人"** | Google OIDC / 自建账号 / 一次性配对码 | **MVP 用配对码 → 正式版自建账号** | 他的 Google 登录在大陆网络第一步就打不开；我们只是自己用，不需要第三方身份 |
| **媒体怎么走** | 只打洞 / 打洞 + 自建 TURN | **先只打洞，跑通后再补 TURN** | TURN 是"一定通"的保险，但过它一个字节就是钱；先看打洞成功率，再决定买多少带宽 |

**一个能省掉后面很多麻烦的设计决定：云端协议照抄他的形状。**
我们的 [board/cloudkvm/main.go:52](file:///D:/win_game_project/26_k11c_kvm/board/cloudkvm/main.go#L52) 已经按他的格式写好了
（`offer` 里带 `{sd, ip, iceServers}`，answer 回 base64 的 SDP）。
只要我们的云说同样的话，**设备侧只需要改"连哪台服务器"和"令牌从哪来"**，
将来"用他的云 / 用我们的云"可以随时切，对方要拿我们的板子联调也不用改代码。

### 9.1 目标长这样

```
   家里（NAT 后面，无公网 IP）        一台有公网 IP 的服务器              外面
┌──────────────────────────┐    ┌────────────────────────────┐    ┌──────────────┐
│ K11C 板子                 │    │ ① 网页 + 登录     443/tcp   │    │ 手机 / 公司电脑│
│  fakevo ─► H.265 ─► pion  │出站│ ② 设备 WS         443/tcp   │    │ 浏览器        │
│  (cloudkvm)               │───►│ ③ TURN 临时凭据   443/tcp   │◄──►│ 什么都不用装  │
│                           │WSS │ ④ coturn STUN/TURN 3478/udp │    │              │
└──────────────────────────┘    └────────────────────────────┘    └──────────────┘
           │                          ▲         ▲                          ▲
           └── 媒体：能直连就 UDP 直连 ─┘         └── 直连不成就从 ④ 中继 ────┘
```

**板子这一侧依然一个入站端口都不开。** 设备只做两件出站的事：① 连信令 WS；② 往 STUN/TURN 和对端发 UDP。
洞是设备自己挖的 —— 这就是整套方案能绕过家用路由器设置的全部秘密。

### 9.2 六步，按顺序做

#### 第 1 步：买服务器 + 域名 + 证书（约半天）

做什么：

1. 香港轻量云 **2C2G / Debian 12**，安全组放行：`80/tcp`、`443/tcp`、`3478/udp`、`3478/tcp`、`49160-49200/udp`。
2. 域名加一条 A 记录 `kvm.你的域名` → 服务器 IP。
3. 装 Caddy 守着 443，证书自动申请和续期：

```bash
# 服务器上
caddy reverse-proxy --from kvm.example.com --to 127.0.0.1:8080
```

怎么算做完：

```bash
curl -s https://kvm.example.com/healthz          # 返回 ok
echo | openssl s_client -connect kvm.example.com:443 2>/dev/null | grep 'Verify return'
# 第二行要出现 Verify return code: 0 (ok)
```

⚠️ **板子这边的坑（很容易被当成"网络不通"）**：RK3566 一般没有 RTC 电池，断电后开机时间是 1970 年，
**TLS 握手会因为"证书还没生效"直接失败**。所以设备侧第一件事是 NTP 对时，对上了再连云。
后面所有"怎么连都连不上"的怪现象，先回来看这一条。

#### 第 2 步：云端骨架（一个 Go 二进制，一张路由表，约 1 天）

先把接口定死，少一个都不写：

| 路由 | 谁调 | 要不要登录 | 干什么 |
|---|---|---|---|
| `GET /healthz` | 运维 | 否 | 健康检查 |
| `POST /api/claim` | 浏览器 | 是 | 输入配对码 → 把这台设备绑到你名下 |
| `POST /api/device/token` | 板子 | 配对码 | 换成长期 `secretToken`（40 位 hex） |
| `POST /api/login` | 浏览器 | 否 | 密码 → 会话 cookie |
| `GET /api/devices` | 浏览器 | 是 | 我有哪几台、在线 / 被占用 |
| `POST /api/devices/:id/offer` | 浏览器 | 是 | 把 offer 转给设备，等 answer 后原样返回 |
| `POST /api/devices/:id/bye` | 浏览器 | 是 | 挂断（触发"清 HID"） |
| `GET /api/turn` | 浏览器 | 是 | 现签一个 10 分钟有效的 TURN 账号密码 |
| `GET /ws/device` | 板子 | Bearer | **整条链上唯一的 WebSocket** |
| `/` | 浏览器 | 否 | 静态页面 |

**为什么浏览器不建 WS**：我们的设备侧是 non-trickle（候选收齐才发 answer），一次 `offer`/`answer` 就够，
浏览器只要一个 HTTP POST。省掉整套"房间管理 / 断线重连 / 消息路由"。

怎么算做完：

```bash
# 终端 A 冒充板子（带 Bearer 连上后不退出）
wscat -c "wss://kvm.example.com/ws/device" -H "Authorization: Bearer <token>"
# 终端 B 冒充浏览器
curl -X POST https://kvm.example.com/api/devices/xxx/offer -d @offer.json
# 期望：A 收到一条 {"type":"offer",...}，B 拿到 {"type":"answer",...}
```

#### 第 3 步：设备侧改造（现有 cloudkvm 改 6 处，约半天到一天）

| 改哪 | 现在 | 改成 | 为什么 |

#### 第 4 步：把信令协议抄下来（半天，但要想清楚再写）

| 消息 | 方向 | 载荷 | 说明 |
|---|---|---|---|
| `ping` / `pong` | 双向 | — | 10 秒一次，兼做 NAT 保活（不 ping，家用 NAT 几十秒就丢映射） |
| `offer` | 云 → 设备 | `{sd, ip, iceServers}` | `sd` = base64(JSON{type,sdp})；`ip` = **云看到的设备公网 IP**；`iceServers` = STUN 列表 |
| `answer` | 设备 → 云 | `base64(JSON{type,sdp})` | 和我们已跑通的那版一致 |
| `bye` | 云 → 设备 | `{reason}` | 浏览器挂断 / 超时 / 被顶掉 |
| `busy` | 云 → 设备 | `{viewer}` | 可选；不做互斥时跳过 |

**两条铁律**（照他的 `cloud.go` 抄的，也是我们目前缺的）：

1. **一次只服务一个人**。第二个人进来，要么告诉他"忙"，要么走"协商成功才顶掉"，**绝不能一进门就踢人**。
2. **会话结束必须清 HID**：对方挂断、超时、WS 断开，三种情况都要发"全零报告"，而且要在关连接**之前**发。

#### 第 5 步：ICE —— 先打洞，再上 TURN（约 1 天）

**设备侧**，公网地址有两个来源，取其一就够：

* **云注入（推荐先做）**：云在 WS 握手里拿到设备的公网 IP，放进 `offer.data.ip`；设备把它当作 `srflx`
  候选塞进自己的候选表。我们已经这么做了（`SetICEAddressRewriteRules`，**实测 1 秒内连上**），
  好处是**完全不依赖板子能不能访问 STUN 服务器**。
  它的软肋：注入的只有**地址**，端口是板子自己的本地端口 —— 遇到对称 NAT 可能打不通，【未证】我们这边宽带是不是对称型，
  测法就是看蜂窝连家里时走的是 `srflx` 还是 `relay`。
* **自建 STUN**：coturn 只开 STUN，设备自己去问"你看我是谁"。它比云注入多验证一步"端口也能通"，但要求板子能访问 3478。

**浏览器侧**：`iceServers` 里同时给 STUN 和 TURN，TURN 凭据**现签、短命**：

```
username   = "<过期时间戳>:<随机串>"
credential = base64(HMAC-SHA1(TURN_SECRET, username))
```

coturn 开 `use-auth-secret`，`TURN_SECRET` 只放服务器环境变量，**不进仓库**。
TURN 最终还要开 `turns:443`（TCP 443 走 TLS）—— 公司网络封 UDP 时这条是唯一活路，
但它会和 Caddy 抢 443，**先别做，等真遇到封 UDP 的网再说**（见 §9.3 第 7 条）。

验收矩阵（三个场景都要过）：

| 场景 | 期望走的路 | 判据 |
|---|---|---|
| 同一 WiFi | `host` 候选 | 不走公网，延迟 ≈ 局域网 |
| 手机蜂窝 → 家宽 | `srflx/srflx` | 最常见，P2P 成功 |
| 公司网络（封 UDP） | `relay` | 必须能靠 `turns:443` 起来 |

**最该盯的运维指标：P2P 成功率。** 云端每次会话记一笔"direct 还是 relay"，这个比例决定你要不要买大带宽。

#### 第 6 步：前端页面（约 1 天）

* 骨架直接沿用 [board/www/index.html:265](file:///D:/win_game_project/26_k11c_kvm/board/www/index.html#L265) 的 datachannel 部分
  （`rpc` / `hidrpc` 帧格式我们已经跑通），只换两处：
  信令从"板子 :8001"换成"云的 `POST /api/devices/:id/offer`"；**offer 改由浏览器生成**（设备侧答 answer，和我们已跑通的一模一样）。
* JetKVM 的前端确实开源，但**抄之前先确认许可证**；我们是产品方向，别把 GPL/AGPL 代码带进来。
  稳妥做法是只参考交互，代码自己写 —— 我们现在的页面本来就是自己写的。
* 怎么算做完：手机切 4G 打开 `https://kvm.example.com` → 看到码表 → 打开记事本打字 → 鼠标能点。

### 9.3 七个最容易把人坑住的地方

1. **时钟**：无 RTC，开机先 NTP。这条能伪装成任何网络故障。
2. **家宽上行**：1080p60 按 6 Mbps 算，家里上行要 ≥ 10 Mbps 才稳。上行 20M 的套餐随便；上行小的就把 `bps` 降到 3M 或降到 30fps。
3. **对称 NAT + TURN 流量 = 钱**：6 Mbps 跑 1 小时 ≈ 2.7 GB（单向）。每天看 2 小时 ≈ 160 GB/月；
   如果运营商出入都计费、且全程走中继，按 320 GB/月估。轻量套餐一般带 1 TB，够自己用，**但别拿它当 24 小时监控**。
4. **WiFi 省电会断连**：板子挂 24 小时，WiFi 芯片可能进省电模式掉线。心跳 + 自动重连是必须的，必要时关省电。
5. **`:8000` 现在零鉴权**：谁能连上谁就能注入键盘鼠标（= 拿到被控机完全控制权）。它**只能监听 `127.0.0.1`**，
   绝不能因为"想远程调试"就映射出去。
6. **令牌与日志**：`secretToken`、TURN 密钥、登录密码哈希都不进仓库、不打进日志。
   我们已经踩过一次"公开仓库里写着明文口令"的坑，别再踩第二次。
7. **443 端口只有一份**：Caddy 要 443（网页 + WS），coturn 的 `turns:` 也想要 443，**两者会打架**。
   三个解法：① 服务器配两个公网 IP 各占一个；② 用 SNI 分流（HAProxy / sniproxy 按域名把 443 分给两边）；
   ③ **先用 3478 跑通，等"公司网络实测确实连不上"再去折腾 `turns:443`**。建议选 ③ —— 顺序反了会在这卡两天。

### 9.4 里程碑：先做哪几步最划算

| 里程碑 | 包含 | 工作量 | 做完能看到什么 |
|---|---|---|---|
| **M0** 能出画 | 第 1 步 + 第 2 步最小版 + 第 3 步只改服务器地址 + 第 6 步单设备版（登录先用一次性 token 顶着） | 1.5~2 人日 | 外面的电脑打开网址，**能出画面、能点鼠标** |
| **M1** 不用管板子 | 配对码 + `/etc` 状态 + systemd + NTP + 重连 + 第 4 步协议定死 | 1 人日 | 断电重启自动上线 |
| **M2** 不互相干扰 | 登录 + 设备列表 + 会话互斥 + 清 HID | 1 人日 | 两个人不会打架，掉线不卡键 |
| **M3** 什么网都能用 | coturn + 临时凭据 + 三场景实测 | 1 人日 | 公司网络、手机蜂窝都能用 |
| **M4** 能长期跑 | 指标 / 限速 / 证书 / 日志脱敏 + 蜂窝延迟实测 | 1 人日 | 挂着不管也不会出事 |

合计 **约 5~6 人日**。其中真正改板子代码的只有第 3 步那 1 人日，分散在 M0~M2 里；其余全在服务器上。
