## 🔱 2026-09-06 方向大切换:放弃"系统采集 API",改"AudioFlinger 内部直接取数"

> 这一节是当前有效方案。下面的旧章节(进展快照、三路对比、历史增补)是踩坑档案,
> 结论以本节为准。

### 三个硬件/分层事实(同事拍板,推翻此前假设)

| 事实 | 推翻/明确了什么 |
|------|----------------|
| **3.5mm 耳机口物理不通** | 09-05 的"虚拟耳机 + WIRED_HEADPHONE 重路由"整条路作废(硬件死路,不是软件能救的) |
| **坏的只是 tinyALSA/PAL 层**(SPEAKER write 永久阻塞,09-05 已抓到铁证:Total writes=4, Blocked=yes) | 任何要求数据"掉进 ALSA 再回来"的路都不通——REMOTE_SUBMIX 镜像也依赖输出线程在跑 |
| **AudioFlinger 框架层是好的** | 数据应该在 AF 层就截走,根本不用等它下去 HAL |

### 新路线一句话

**游戏声音从蓝牙音箱出** + **在 AudioFlinger 源码里加 per-track 导出口子**,
把"游戏那一轨"的原始 PCM 直接抄给 HapticX——完全绕开残缺的 HAL 和整套采集 API。

```
老路(已废弃):  游戏轨 → AF混音 → [REMOTE_SUBMIX 影子轨镜像] → AudioRecord → HapticX
                                ↑ QCOM BSP 上影子轨不激活 + 混进了系统音 + 依赖输出线程活着

新路(拍板):    游戏轨 ─→ Track::getNextBuffer hook ★混音前抄走原始 PCM★ → socket → HapticX
               游戏轨 ─→ AF混音 → 蓝牙A2DP(独立HAL,不碰tinyalsa) → 玩家听声
```

### 为什么 per-track 取数更干净(同事原话展开)

1. **取数点在混音之前**——拿到的是游戏轨"独奏",没有 UI 音/通知音混进来,
   低频分析不再被系统提示音污染
2. **不挑输出线程**——DIRECT/offload 直通、MIXER、FAST,所有 track 都过
   `getNextBuffer`,09-04 发现的"mono 被 DIRECT 吃掉"问题**直接免疫**
3. **绕开整套采集授权/影子轨机制**——不再跟 policy mix、secondary outputs
   这些 QCOM BSP 坑缠斗(09-03/09-04 已充分踩过,详见文末增补)
4. **到了 ALSA 层就全是混好的了**——再想分离已经不可能,所以必须上移取数点

### 为什么蓝牙不只是"能出声",而是数据流动的引擎(关键认知)

AF 里所有轨道的数据,都是**输出线程的 threadLoop 循环"拉"出来的**。
primary 输出卡死在 SPEAKER HAL write → 挂在它上面的轨道一动不动 →
任何 hook 都没数据可抄(这就是 09-05 之前的全部静音的底层原因)。

蓝牙 A2DP 是**独立的 hw module + 独立 HAL**(socket 通往蓝牙协议栈,
完全不碰 tinyalsa),它的混音线程正常循环 → 游戏轨挂上去,数据自然流起来,
hook 才有东西可抄。**所以"连上蓝牙"是硬前提,不是体验优化。**

### AF per-track hook 技术设计

| 设计点 | 选择 | 理由 |
|--------|------|------|
| hook 位置 | `TrackBase`/`Track::getNextBuffer` 返回后(frameworks/av/services/audioflinger/Tracks.cpp) | 每个 track 被混音器拉数据的必经点;拿到的是该轨原始 PCM |
| 过滤条件 | `attributes.usage == AUDIO_USAGE_GAME`(属性可配:`persist.vendor.hapticx.hook_usage`) | 只抄游戏轨;uid/包名过滤留作扩展 |
| 导出通道 | Unix domain socket(AF 写端 / HapticX native 读端) | 48kHz/16bit/stereo = 192KB/s,本地 socket 轻松扛;memfd ring buffer 留作优化 |
| 防御性 | socket 无人收/发送失败 → 丢帧,**绝不阻塞 threadLoop** | audioserver 是整机音频的心脏,不能被 app 拖死(09-04 的 watchdog 死锁教训) |
| 改哪棵树 | **LA.QSSI.15.0-irix** 的 frameworks/av/services/audioflinger | audioflinger 在 system 分区(QSSI 侧)——注意和 audiopolicy 同侧,不碰 VENDOR 树 |
| 迭代方式 | 增量编单模块 + push .so + `killall audioserver` | 09-05 已用 build_apm.sh 验证单模块增量编译可行(MODULES-IN-... 同套路),**分钟级,不用 6h 整包** |

## 30 秒速览(TL;DR)

目标：在 Qualcomm QCS8550 安卓 15 掌机（固件音频栈残缺）上，捕获**游戏音频 PCM**，实时分析并驱动手柄马达震动（"雷云"功能）。

**已确认的固件级事实**：
- SPEAKER HAL 的 `write()` **永久阻塞**（固件 bug，tinyalsa/PAL 层坏）
- PAL（QCOM 音频 HAL 层）的 **PCM 流→A2DP 蓝牙**路径**同步挂死**（futex 死锁，导致 audioserver 崩溃）
- PAL 的 **AAC 压缩流（offload/direct）→A2DP** 路径**正常**（实测出声，信号 -11.7dB 真实流动）
- 3.5mm 耳机口物理不通（硬件事实，不试）

**当前卡点（核心）**：AudioFlinger 的所有播放轨数据都由**输出线程 threadLoop 主动"拉"**出来（HAL write 驱动）。**所有 PCM 输出线程在这台机器上全部挂死**（SPEAKER 挂、A2DP 挂），因此：
- 官方捕获 API（AudioPlaybackCapture，依赖 REMOTE_SUBMIX 镜像轨）→ 镜像轨创建后 0.5s 被移除，采到纯静音
- 同事建议的 AF 层 per-track hook（改 AudioFlinger 源码在 `Track::getNextBuffer` 抄数据）→ **同样依赖输出线程拉数据，同样会挂**

**请回答的核心问题**：在所有 PCM 输出线程挂死的前提下，AF 层还有什么取数点不依赖输出线程？详见下方「重点问题」节。

## 项目目标

- 设备：SNM970/OK700 掌机（Qualcomm QCS8550，即 kalama 平台）
- 系统：Android 15，QCOM BSP = `LA.VENDOR.15.4.3`（vendor 侧）+ `LA.QSSI.15.0`（system 侧）
- 应用：HapticX（预装 priv-app），申请 MediaProjection → 捕获**其他 app（游戏）的音频** → A2HAnalyzer 频段分析 → 输出到手柄马达
- 音频输出设备：**蓝牙 A2DP 音箱**（SPEAKER/3.5mm 均不可用）
- 音频栈代码位置：audioflinger/audiopolicy 在 **QSSI 树 system 侧**（`frameworks/av/services/`），可单模块增量编译 + push .so + killall audioserver 分钟级迭代。PAL 在 vendor 侧（闭源 .so，不可改）。

## 架构背景：安卓音频栈与两条取数路线

### 数据流（正常机器）

```
游戏 app (AudioTrack write PCM)
  → AudioFlinger: Track（每个 app 一条，挂在某个输出线程上）
  → 输出线程 threadLoop: AudioMixer 混音 ← 关键：所有轨的数据都是 threadLoop 循环"拉"出来的
  → HAL write (vendor: PAL → ADSP/蓝牙)
```

### 路线 A：官方捕获 API（AudioPlaybackCapture）——app 层拦截（已废弃）

```
捕获激活 → APM 创建 REMOTE_SUBMIX 输出
  → 每条播放轨在 REMOTE_SUBMIX 输出线程上创建"镜像轨"(mirror track)
  → 源轨数据被源输出线程拉动的同一时刻，复制到镜像轨
  → REMOTE_SUBMIX 线程把镜像轨数据混音后送给捕获方 AudioRecord
```

**致命依赖**：镜像轨的数据同样来自"输出线程拉动"。源轨挂死的输出线程上 → 源轨数据不流 → 镜像轨永远无数据（FrmRdy=0）→ 0.5s 后被 AF 回收。**输入侧（AudioRecord）完全健康，只是喂给它的都是静音。**

### 路线 B：AF 层 per-track hook（同事拍板路线）

```
改 AudioFlinger 源码（Tracks.cpp 的 Track::getNextBuffer）
  → 在混音器从游戏轨取 buffer 时顺手复制一份原始 PCM
  → 通过 Unix socket 送给 HapticX app
```

**同样致命**：`getNextBuffer` 由 AudioMixer 调用，AudioMixer 由输出线程 threadLoop 驱动。输出线程挂死 → hook 永远不被调用。**两条路线卡在同一个硬前提上。**

### 已做的 APM 补丁（路线 A 的救活尝试）

两处修改（都在 QSSI 树 `frameworks/av/services/audiopolicy/managerdefault/AudioPolicyManager.cpp`，日志标记 `SNM970APM`）：

**补丁 1**：`getNewOutputDevices()` —— 捕获激活时，若输出设备是挂死的 SPEAKER 且 A2DP 可用，强制 reroute 到 A2DP：

```cpp
// 位置:AudioPolicyManager::getNewOutputDevices() 开头附近
if (mPolicyMixes.needsMirroring(...)) { /* playback capture active */ }
    DeviceVector btDevices = mAvailableOutputDevices.getFirstDevicesFromTypes(
            {AUDIO_DEVICE_OUT_BLUETOOTH_A2DP});
    ALOGD("SNM970APM: btDevices count=%zu", btDevices.size());
    if (!btDevices.isEmpty()) {
        sp<DeviceDescriptor> btDevice = btDevices.itemAt(0);
        ALOGD("%s: playback capture active, output %d rerouted from %s onto %s", __func__,
                outputDesc->getId(), outputDesc->devices().toString().c_str(),
                btDevice->toString().c_str());
        return DeviceVector(btDevice);   // 强制 A2DP
    }
```

**补丁 2**：`getOutputForDevices()`（09-05 加）—— 捕获激活时保持 stream MUSIC 在 mixer 路径（阻止退到 offload/direct，因为镜像轨只在 mixer 路径工作），日志 `keep stream %d on mixer path`。

**补丁 3（09-06 修的 bug）**：09-05 版补丁 2 里误加了 `!playbackCaptureActive` 到 forceDeepBuffer 条件，导致捕获激活时测试音轨 flags 退成 NONE，被兜底到 primary FAST 输出（绑 SPEAKER，F2 挂死）。已删除该条件，测试音正确回到 deep_buffer 输出，且补丁 1 成功把它 reroute 到 A2DP——然后撞上 F4/F5（PCM→A2DP 挂死+崩溃）。

## 当前卡点的精确技术描述

1. **测试音（PCM, MUSIC usage）在捕获激活时的路径**：app AudioTrack → AF Track → deep_buffer 输出线程（补丁 3 修复后不再掉到 primary FAST）
2. **APM 补丁 1 生效**：捕获激活 → `setOutputDevices(A2DP)` → logcat 确认 `out=9 rerouted from {AUDIO_DEVICE_OUT_SPEAKER} onto {AUDIO_DEVICE_OUT_BLUETOOTH_A2DP}`
3. **AF 执行 reroute**：deep_buffer 线程收到 patch 事件，尝试经 PAL 重新打开 A2DP 输出流（PCM 格式）
4. **PAL 打开 PCM→A2DP 流时同步挂死**（futex_wait，无 PAL 流日志输出，挂点在 PAL 内部，闭源不可查）
5. **连锁崩溃**：APM 的 binder 线程持 APM::mLock 同步等待 → 其他 binder 调用（如 setPhoneState）排队 10 秒 → TimeCheck abort → audioserver 被 SIGABRT → 捕获中断
6. **重启 audioserver 后死循环**：每次重测都在第 4 步重挂

**注**：AAC 压缩流→A2DP（DIRECT 线程，PAL BT offload 插件）**不挂**。差别只在 PCM vs 压缩数据格式。QCOM 这个 PAL 版本的 A2DP PCM 插件（软编码路径，走 primary HAL）疑似有 bug——但 09-06 早些时候 AAC 软编码（也是软路径）是通的，所以更可能是 **PCM 格式的 a2dp output stream open** 路径有独立 bug（如等待某个永不来的 codec ready 回调）。

## 候选方案（按当前评估状态排序）

### 方案 A：恢复 policy 配置的蓝牙独立 HAL 模块 ⭐当前执行中
- 做法：apc_bt.xml——取消注释并启用 bluetooth 模块（`audio.bluetooth.default`，AOSP 蓝牙软编码 HAL，userspace，不经 PAL），同时注释 primary 模块的 A2DP 设备端口
- 依据：E6/F12 —— 独立 HAL 存在，APM 路由改造已验证成功；PAL PCM→A2DP 挂死只是 PAL 内部 bug，绕开它
- 卡点：F13 —— BT 栈不启动软编码 session 1（见最新进展，修复方案已定）
- 若成功：deep_buffer PCM→bluetooth HAL→蓝牙音箱出声 + 输出线程活 → **镜像轨/AF hook 整条链路复活**

### 方案 B：AF per-track hook（同事原方案，09-07 拍板执行）
- 在 `frameworks/av/services/audioflinger/Tracks.cpp` `Track::getNextBuffer` / mixer 取数路径抄 PCM → Unix socket 给 app
- **与方案 A 是"或"关系吗？** —— 不是，B 依然依赖输出线程活着（threadLoop 驱动 getNextBuffer）。**B 必须叠加 A（或任何让输出线程活着的手段）才成立**。A 成功后，B 相比官方 API 的优势仅剩"只取游戏轨、更干净、不触发系统捕获模式"
- 成本：改 AF 源码 + 每次迭代重编 push（可行，QSSI 树侧）

### 方案 C：压缩域 hook（DIRECT 线程取 AAC）
- DIRECT 线程→A2DP 是唯一已实测活着的数据通路（F3）。在 DIRECT 线程 hook 取 AAC 帧 → app 内软解 AAC → PCM 分析
- 难点：AAC ADTS 帧解析/解码在 app 侧可行（MediaCodec），但游戏音轨是否走 offload 取决于 content type（游戏多用 AudioTrack PCM，不是压缩流）——**游戏音大概率根本不走 DIRECT**，此方案可能只能捕获音乐/视频类 app
- 捕获激活时框架还会主动把轨从 offload 退到 mixer（F10），进一步压缩适用面

### 方案 D：USB 声卡（零代码备胎）
- USB audio 走独立 `usb` HAL 模块（policy 配置里存在且启用），完全不碰 PAL
- 插 USB-C 声卡 → PCM 输出走 usb HAL → 输出线程活 → 捕获镜像轨活
- 缺点：掌机形态需外接硬件；但作为**验证"输出线程活了捕获就通"的对照实验**成本极低

### 方案 E（远期）：修复 vendor 侧 PAL
- 闭源，无源码，除非拿 QCOM CASE 支持。已放弃。

### 蓝牙音频 AIDL session 机制剖析（logcat 时间线 + QTI 源码交叉验证）

```
蓝牙音频 AIDL 架构（本机实测角色分工）:
  audio service (android.hardware.audio.service_64, pid 5533)
    └─ 承载 IBluetoothAudioProviderFactory/default（BTAudioProviderFactoryAIDL）
       └─ 承载两类 provider stub（BTAudioProviderStub）
            ├─ session 1 = A2DP_SOFTWARE_ENCODING_DATAPATH   ← audio.bluetooth.default 需要
            └─ session 2 = A2DP_HARDWARE_OFFLOAD_ENCODING_DATAPATH ← PAL BT 插件用（传压缩帧）
  BT 栈 (com.android.bluetooth, pid 6767)
    └─ 客户端: FetchAudioProvider/openProvider 只是拿到 provider 对象
       ★ startSession 之后会话才算"就绪"，HAL 侧才能开流
```

**关键规则（本卡点的根因）**：BT 栈对 A2DP **一次只启动一个 datapath session**，类型由 offload 决策决定：
- offload 启用 → 起 **session 2**（HAL 交压缩帧，BT 栈直接转发）——**之前 mp3/ogg 能出声，
  走的就是这条路**：PAL 把 AAC 压缩帧交给 session 2 的 datapath
- offload 禁用 → 起 **session 1**（HAL 交 PCM，BT 栈内软编码再发）——**audio.bluetooth.default
  需要的正是它**

```

persist.bluetooth.a2dp_offload.disabled  = false   ← offload 启用中
persist.bluetooth.a2dp_offload.cap       = sbc-aac-aptx-aptxhd-ldac
```

### 卡点的最终真相:三张互不相通的 session 表

上一个方案(apc_bt.xml,激活 bluetooth 模块)失败的根因不是 session 没启动,
而是**库链错配**——同一进程里有三套蓝牙 session 实现,各自一张静态表:

| 库文件 | 链接的 session 库 | 角色 |
|--------|------------------|------|
| `audio.bluetooth.default.so` (AOSP) | `libbluetooth_audio_session_aidl.so` | ❌ 孤儿表:provider 工厂不在它这,永远空 |
| `android.hardware.bluetooth.audio-impl-qti.so` | `libbluetooth_audio_session_aidl_qti.so` | ★ provider 工厂,BT 栈 startSession 写进这张表 |
| `audio.bluetooth_qti.default.so` (QTI) | `libbluetooth_audio_session_aidl_qti.so` + 直接依赖 impl-qti | ✅ **与工厂同一张表** |

铁证(logcat):BT 栈 `startSession - A2DP_SOFTWARE_ENCODING_DATAPATH` 成功 5 秒后,
AOSP 库 `init_session_type ... is not ready`——**session 在 QTI 的表里,它查的是自己的空表**。
QTI 源码 `vendor/qcom/proprietary/bluetooth/audio_bluetooth_qti_hw/Android.bp` 证实:
`audio.bluetooth_qti.default` 的 shared_libs 里同时有 `android.hardware.bluetooth.audio-impl-qti`
和 `libbluetooth_audio_session_aidl_qti`——工厂和 HAL 天生共享一张表。

**为什么 bluetooth_qti 模块开机就存在?** 它由
`/vendor/etc/bluetooth_qti_hearing_aid_audio_policy_configuration.xml` 定义(hearing aid 用),
加载 `audio.bluetooth_qti.default.so`,顺带把 provider 工厂注册进了 audio 服务进程。

## 📌 2026-09-04 增补二：根因重大修正——mono→DIRECT 直通

用 AudioFlinger dump 对拍测试音的 track 归属，**推翻/修正了昨天"BSP secondary outputs 失效"的笼统结论**，定位到精确机制：

### 决定性证据
| 测试音构造 | track flags | 路由去向 | secondary outputs |
|---|---|---|---|
| MODE_STATIC + mono | 0x200 (FAST) | AudioOut_5D (DIRECT) | 无（直通） |
| MODE_STREAM + mono | 0x000 | **AudioOut_5D (DIRECT)** | 无（直通） |
| （真实游戏 stereo） | — | AudioOut_D (MIXER) | 才有 |

- `AudioOut_D`（primary MIXER）`AudioStreamOut flags 0x6 = PRIMARY|FAST`，跑 FastMixer
- `AudioOut_5D`（DIRECT 线程）`flags 0x1 = DIRECT`，device=SPEAKER，mono 流被高通 BSP 选它直通
- **只有 stereo 走 MIXER 才会触发播放采集的 secondary outputs（TeePatch 影子轨）**

### 修正后的判断
- 之前 PPSSPP(OpenSL)、AOSP Music 采集不到，**尚未在 stereo MIXER 轨上验证过**——之前的测试音全是 mono，全被 DIRECT 直通吃掉，测了个寂寞
- 已改 TonePlayer：`MODE_STATIC→MODE_STREAM`、`mono→stereo`，对齐真实游戏场景
- **待验证**：stereo 测试音是否进 AudioOut_D(MIXER) + 影子轨激活 + 采集电平>0
  - stereo 能采到 → 根因就是 mono 直通，采集端改 stereo 或强制 MIXER 即可（APK 层可修）
  - stereo 仍采不到 → 才回到 BSP 深挖（FastMixer 场景下 secondary outputs 激活）

### 调试环境注意
设备经反复 force-stop + killall audioserver 后进入脏状态：Binder NPE（getMediaProjection 同步异常）、`Content Recording: Stopped due to foreground service change`、投影反复 stop。**stereo 终验需重启板子用干净环境**。

### 蓝牙实测结果（同事的判断验证）

| 测试 | 结果 | 数据 |
|---|---|---|
| A2DP 连接 | ✅ AAC 44.1k 协商成功 | `A2dpStateMachine mConnectionState: CONNECTED` |

### 关键架构事实（刷新认知）

1. **policy 配置里 a2dp 模块是被注释掉的**——蓝牙输出走的是 primary 模块 PAL 的 BT 插件（AAC 软件编码，不经 ADSP 硬件通路），这就是 A2DP 能活而 SPEAKER 死的原因
2. **ADSP running**（remoteproc 查证），speaker 挂不是 ADSP 没起
3. **PAL 的两条路命运不同**：BT 流（软编码）✅ / SPEAKER 流（硬件通路）❌ 永久挂起

### 终审证据：两条卡死的 primary 混音线程

| 线程 | flags | 卡点 | 症状 |
|---|---|---|---|
| AudioOut_D | PRIMARY\|FAST | HAL **write** | 4 次写入后永久阻塞 |
| **AudioOut_25** | **DEEP_BUFFER** | **standby 退出**（PAL speaker 流启动） | **16 条活跃音轨数据全满（HapticX 测试音 240000 帧×7、游戏轨 usage=GAME、ogg 轨），0 次写入，Standby: yes** |

**全部 PCM 音频（游戏/测试音/UI 声）都堆在 AudioOut_25 上冻着**——
混音循环从未跑起来，所以：
- 玩家听不到（PCM 在这台机器上根本是哑的，蓝牙只救了压缩音乐）
- 镜像轨（REMOTE_SUBMIX）每次播放都会创建，但源轨不动 → 镜像永不激活 → 移除
- app 从 submix 管道里读到的全是被写入的"静音填充"

另验证 AOSP 行为：**捕获激活时 MEDIA 轨自动从 offload 退到 deep_buffer**（第二轮 ogg 不走 DIRECT 了）——框架在配合，硬件通路死了。

### 结论与下一步（比 AF hook 更便宜的路先走）

**堵点只剩一个：让 deep_buffer 线程别在 SPEAKER 上启动。**
DIRECT 线程能以 A2DP 设备打开并流畅写入（PAL BT 路通），说明
**primary 模块的混音线程以 A2DP 打开大概率同样能跑**。

修订计划（优先级序）：
1. **小改 APM**（~30 行，build_apm.sh 分钟级迭代）：
   音轨启动时若输出设备是 SPEAKER 且 A2DP 可用 → setOutputDevices(A2DP)。
   顺序关键：必须在音轨激活**之前**完成切换（线程一旦卡死就再也听不进 patch 事件）
2. 验证顺序：推 so → killall audioserver（BT 已连）→ HapticX 自播自采 →
   期望：**耳机出声 + peak>0**。若成，**原 app+捕获 API 架构直接复活，AF hook 不需要**
3. 镜像若仍不激活 → 再上 AF per-track hook（此时线程活着，hook 有数据可抄）
4. 零代码备胎：USB 声卡走 usb 模块（独立 HAL 完全绕开 PAL），同样能让 PCM 流动 + 验证镜像

### 三、第三步提前开跑：GIP 会话半逆向（sendgip 工具 6 版迭代）

新工具 `sendgip.c` + 脚本 `gip_exp.sh`（同目录）：unbind xpad →
usbfs 直发任意 GIP 包到 ep_05 → 监听 ep_84 并打印设备回话。
它揭示了 xpad 绑定时**永远看不到的另一半对话**：

**发现 1：设备一直在"敲门"，Linux 从不开门**
```
设备 → host: 03 20 <seq> 04 80 ...   ← GIP announce（flags=0x20 要求 ack）
```
BSP xpad 的 `xpadone_process_packet` 只处理 0x07（guide 键）和
0x20（input report），**对 0x03 announce 直接丢弃、从不回 ack**。
设备等不到 ack 会周期性重置 USB 重新枚举（devnum 009→010 就是这么来的）。

**发现 2：GIP 握手是"连环"的**
- power mode init（`05 20 00 01 00`，xpad 绑定时发的唯一 init）会
  触发 announce
- ack 一个 announce，设备接着发下一个（seq+1），直到会话稳定
- Windows 的 XboxGip.sys 本质是个**全自动 ack 引擎**

**发现 3：ack 格式的正确写法（走了两次弯路才对）**
- ❌ 第一次：`02 00 ...` —— 0x02 是 ANNOUNCE 不是 ack，把 announce
  发回给设备，它连环重发 chunk 包停不下来
- ✅ 正解（xone 驱动 protocol.c `gip_acknowledge_pkt` 对照，仓库
  dlundqvist/xone）：**0x01 = ACKNOWLEDGE**，13 字节：
  ```
  01 20 <对方seq> 09 {00, <被ack命令>, 20, <length:LE16>, pad2, <remaining:LE16>}
  ```
- 正确 ack 发出后，设备那串 `03 a0` chunk 包**停了**（错误 ack 时
  无限重发）——证明设备认了我们的 ack，会话半激活

**发现 4（当前卡点）：会话"半激活"状态下 rumble 仍不震**
- 最新一轮：正确格式 ack 引擎持续握手 + 会话活跃（chunk 流被 ack
  止住）+ rumble 准时发出（USB 层成功）
- **手柄依然不震**，且 rumble 后 IN 转静默（连 input report 都停）
- 推测：Windows host 在握手后还有我们没发的命令（开启 input
  streaming / 设备就绪通知等），或 rumble 包字段有 Razer 特有差异

### 四、当前结论与下一步

| 假说 | 状态 |

### 关键新事实（全部实测）

1. **主线 commit e2b0ae5（已进 5.15/6.6/6.12 stable）**：Wolverine V3 Pro 有线 0x0a57 / dongle 0x0a59 被标为 **XTYPE_XBOX360**，

## 📌 2026-09-09：PID 模式定标 + xpad 源码真相（记忆锚点）

> 本轮查主线 xpad.c 源码，厘清了一个此前反复混淆的关键事实。

### 一、两个 PID 到底谁是 PC 模式（已定标，勿再搞混）

| PID | 模式本质 | Windows 维持方式 | xpad 分类 |
|---|---|---|---|
| **0x0a4c** | **PC / Xbox360 模式**（PC Persona）✅ | xusb22.sys/XInput 完整握手，把模式锁写入手柄 NVM 持久化 | 命中 `XPAD_XBOX360_VENDOR` 通配 → XTYPE_XBOX360 |
| **0x0a3f** | **GIP / 雷蛇预设模式**（雷云 2.4G 收发器同款 ID） | XboxGip.sys（GIP 模式）或 xusb22.sys（PC 模式）都能震 | 命中 `XPAD_XBOXONE_VENDOR` 通配 → XTYPE_XBOXONE |

**结论：0a4c = PC 模式（用户判断正确）；0a3f = GIP/预设模式。**

### 二、xpad.c 的匹配依据（接口描述符，非 PID 精确项）

主线 xpad.c 对 1532 **没有 0a3f/0a4c 的精确条目**，只有两条**接口描述符通配**：

| 通配 | 匹配条件 | 类型 |
|---|---|---|
| `XPAD_XBOX360_VENDOR(0x1532)` | subclass 0x5D(93) / protocol 1 | XTYPE_XBOX360 |
| `XPAD_XBOXONE_VENDOR(0x1532)` | subclass 0x47(71) / protocol 208(0xD0) | XTYPE_XBOXONE |

Razer 的精确条目只有 Atrox(0a00)/Wildcat(0a03)/Wolverine V2(0a29) 三个 XBOXONE。

### 三、为什么 0a4c 闪一下就变回 0a3f（根因）

1. 手柄固件上电按**上次保存的 persona** 枚举 → 在 Windows 用过，保存 PC 模式 → 先以 0a4c 出现。
2. 固件随后等待 host 做 **Xbox 身份确认握手**（identify/announce 应答）。Windows 的 xusb22.sys 会回复并把手柄锁定在 0a4c 持久化。
3. **Linux xpad 从不回复身份确认**，只会发 power_on/led/auth（`xboxone_init_packets[]` 仅 4 种通用包）。
4. 固件等不到正宗 host 确认 → 超时回退默认 GIP/雷蛇形态 0a3f。

**根因不是 rumble 包格式，而是「会话级握手缺失」**——这也解释了为何社区给 0a3f 加 XTYPE_XBOXONE 精确条目照样不震（只改分类，不解决握手）。

### 四、结论与方向

- 0a4c = Xbox360 协议，若稳定，xpad 走 360 分支，rumble 是社区验证过无数次的 360 格式（`00 08 00 ss ww ...`）。
- **性价比最高路径：想办法把 0a4c 锁住**，而非在 0a3f 上继续折腾 GIP。
- 两条可走：① 抓 Windows 枚举握手（场景1前几秒 OUT 序列里找 identify/announce 应答暗号，拿到后 Linux 重放）；② 在 0a4c 出现的瞬间窗口内，用 USB 控制传输推一个 360 握手把 persona 持久化。

### 五、xpad.c 源码定位（复用索引）

- 设备表：`xpad_device[]`（1532 条目）+ `XPAD_XBOX360_VENDOR` / `XPAD_XBOXONE_VENDOR` 宏
- init 包：`xboxone_init_packets[]` = power_on `05 20 00 01 00` / led_on `0a 20 00 03 00 01 14` / auth_done `06 20 00 02 01 00` / rumble_begin（仅特定 PID）
- **源码里没有任何 persona/模式切换命令**——这是 Linux 无法锁定 PC 模式的直接证据。
