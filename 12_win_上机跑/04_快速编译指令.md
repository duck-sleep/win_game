## 脚本到底跑了几步（"给了指令为什么还不管用"的真相）

> 09-11 通读 `SNM970_A15_build.sh` 全文（1-330 行）后整理。**你没有漏看脚本**——
> 脚本里没有藏着"自动清旧产物"的指令。"经常不管用"的锅不在这条命令，在它调用的 `prepare_vendor`。

`./SNM970_A15_build.sh userdebug kalama 01 [inc|full]` 一条命令，main 里固定跑 5~6 个阶段：

| 顺序 | 阶段 | 干什么 | 有没有"清旧产物" |
|---|---|---|---|
| 1 | `build_qssi` | QSSI 框架 `--qssi_only`（full 多一步 update-api） | 交给 Soong/ninja |
| 2 | `build_kernel` | 内核：`kernel_platform/build.sh` → 产 Image/dtbo/.ko 进 dist/ | 内部走缓存，不清 |
| 3 | `copy_kernel` | `rsync -a` dist/ → 上层 out/（无 `--delete`，**残留旧 ko**） | ❌ 正是坑2 |
| 4 | `build_userdebug_target` | **跑 prepare_vendor**（COPY_NEEDED 门控在这）→ 再 `--target_only` 打包 | ❌ 正是坑4 |
| 5 | `generate_dynamic_images` | super.img 合并打包 | — |
| 6 | `generate_ota_package` | 仅 `full` 跑；`inc` 跳过 | — |

**`inc` vs `full` 的唯一差异就 2 处**：full 多跑 `make update-api` + 第 6 步 OTA 包。**两者都不会删 `device/qcom/kalama-kernel/Image`，也都不 `rm out/`**。所以指望"换 full 模式就能刷新产物"是错的——必须手动删 Image。

**为什么不"全自动"**：第 4 步 prepare_vendor 把"内核 dist 产物"当**外部预编译件**铺进 `device/`，它的搬运判断只认 `Image 在不在 + build.config 变没变`，不认源码/dtbo 时间戳。命令层面它给所有阶段发的是同一条，**没有任何自动失效逻辑**，这就是"给了指令也时常不生效"的结构性根因。

## 假成功根因（"觉得编译了、结果没编译上"——务必通读）

> 这是本项目最反复踩的坑族。2026-09-11 结合 SNM970_A15_build.sh、build/build.sh、
> prepare_vendor.sh 源码逐行核对后整理。每条都附源码位置，可信度标注见右。

### 坑 1：run_build 结构性吞错误（`2>&1 > log` 写反） 〔证据：脚本行 ~150〕
`run_build` 内部是：`bash -c "${BUILD_COMMAND}" 2>&1 > ${LOG} || err_exit`
- `2>&1` 先执行：把 stderr 指向"此刻的 stdout = 终端"；
- 然后 `> ${LOG}` 才把 stdout 重定向到文件。
- 结果：**make/gcc 的 error 几乎都走 stderr，全跑到终端一闪而过，build_log/*.txt 里根本没有**。
- 只有退出码非 0 时才 `err_exit` 把日志改名成 `.ERROR.txt`；若错误被子 shell / 管道吞了退出码，日志仍叫 `.txt`、终端还会打 `DONE`。

→ **铁律**：永远 `... 2>&1 | tee build.log`（文档第 2 步那条）。只看 `build_log/make_kernel.txt` 会漏掉真错误。看到 DONE≠成功，产物清单才算数。

### 坑 2：copy_kernel 用 rsync -a，不清理旧产物 〔证据：脚本 copy_kernel 行〕
`rsync -a kernel_platform/out/ out/`（或 `cp -au`），**没有 `--delete`**。
- 你把某驱动从 `=m` 改回 `=y`、或删了源码，旧 `.ko` 仍躺在 `out/` 和 `dist/`；
- 于是"配置改了但 ko 还在"或"以为没编上其实读的是旧 ko"。

→ **铁律**：改内核配置/源码后，验证前先看 `out/.../dist/*.ko` 的时间戳，或直接 `rm -rf out/`（整包）重跑。别信目录里"存在即最新"。

### 坑 3：xone-gip 的符号依赖链（超 ECDSA/HMAC/SHA256） 〔证据：modprobe --dump-modversions 现场 + config 实态核查〕
`xone-gip.ko` 的未决符号不只是文档里列的 ECDSA/HMAC/SHA256，还包括：
- `crypto_ecdh_encode_key` / `crypto_ecdh_key_len` → 需要 `CRYPTO_ECDH`
- `crypto_alloc_kpp` / `crypto_req_done` → 需要 `CRYPTO_KPP`
- `crypto_alloc_akcipher` → 需要 `CRYPTO_AKCIPHER`
- `crypto_shash_tfm_digest` / `crypto_shash_setkey` / `crypto_shash_digest` → 需要 `CRYPTO_SHASH`
- `CRYPTO_ECDSA`、`CRYPTO_HMAC`、`CRYPTO_SHA256`

**关键发现（09-11 实态）**：config 核查显示 `consolidate.config` 里上述符号 **只有 CRYPTO_ECDSA 和 CRYPTO_SHA256 是 =y，CRYPTO_HMAC 是 =0，CRYPTO_ECDH/AKCIPHER/KPP 全是 0**。LEDS_CLASS / LEDS_TRIGGERS 也一样。

→ xone 的符号依赖**不是靠 consolidate.config 自己产生**，全部挂在 **GKI vmlinux 提供的内置符号**上。这也是为什么 modpost 能过（用 GKI 的 Module.symvers 做版本检查），但板上如果 GKI kernel 被裁剪掉任何一项，insmod 直接失败。

**命名纠正**：文档下文和 codebase 里 config 文件名用的是**下划线**（`kalama_GKI.config`、`kalama_consolidate.config`、`kalama-consolidate_defconfig`），路径是 `msm-kernel/arch/arm64/configs/vendor/`——不是连字符。

→ **铁律**：检查 xone 能 insmod 时，除了 "ko 在不在"，还要确认 **板上 GKI kernel 有没有把上述所有 crypto 子系统编译进来**。`CONFIG_CRYPTO_AKCIPHER` 和 `CONFIG_CRYPTO_KPP` 如果被 Qualcomm GKI defconfig 裁成 =n，xone 加载会报 "Unknown symbol"。

### 坑 4：prepare_vendor 的 COPY_NEEDED 门控（最阴的假成功）〔证据：源码 + 2026-09-11 整包现场实测复现〕
xone 这类驱动是 **vendor_dlkm 第二阶段模块**。搬运整段被包在 `if [ "${COPY_NEEDED}" == "1" ]` 里（prepare_vendor 行 280）。而 COPY_NEEDED 只在两种情况置 1（行 201-207）：
- `device/qcom/kalama-kernel/Image` 不存在；或
- `device/qcom/kalama-kernel/build.config` 与 `kernel_platform/build.config` diff 不同。

**致命点**：COPY_NEEDED 的判定**只看 Image 在不在 + build.config 变没变，完全不看 `.config`、驱动源码有没有改**。所以你光加驱动、改 config，它根本不知道要重搬 → `COPY_NEEDED=0` → 跳过搬运 → `device/qcom/kalama-kernel/vendor_dlkm/` 仍是旧的 → 打包用旧 ko → super 里 vendor_dlkm.img 不含新驱动。

**09-11 现场复现（铁证）**：改 xone=`=m` 后整包，`build_kernel` 阶段 dist/ 正常产出 `xone-*.ko`（10:04，编译真成功）；但 `make_userdebug_target.txt` 里**没有 "Preparing prebuilt folder" 那行**（该日志仅 COPY_NEEDED=1 才打印），`device/.../vendor_dlkm/` 里 ko 全是 9 天前的旧文件，`debugfs` 读最终 `vendor_dlkm.img`（302 个 ko）**里没有 xone**。→ xone 编出来了，但被这道门挡在刷机包外。

→ 这就是旧笔记"改内核/DT/.ko 后务必 `rm -f device/qcom/kalama-kernel/Image` 否则增量不动"的**源码级原因**（旧总结方向对，但当时只记了现象、没点透"删 Image 是为了逼 COPY_NEEDED=1 触发搬运"）。

**修复动作（改过 vendor 驱动/内核后，二选一）**：
- 手动 `rm -f device/qcom/kalama-kernel/Image` 再跑 `build_userdebug_target` 阶段 **（推荐）**；
- 整包用 `full` 模式（脚本 `full` 会**不删** device/Image，只会跑 `make_kernel_update` 检查 ABI，**`full` 不等于"从清空开始"**，仍需要手动删 Image 才能触发搬运。）
- **验收**：打包后 `debugfs -R "ls /lib/modules" vendor_dlkm.img | grep xone` 必须能看到，别信 build 没报错。

#### 坑 4b：dtbo 增量过期（同一根因的另一面）〔证据：08-26 现场 + 源码行 201-280〕
**症状**：改了 overlay DTS（如 `kalamap-hdk-overlay.dts`），增量编译跑的"成功"，刷机后板上 dtbo 仍是旧值（`boot-option` 没变、GPIO46 hog 没生效）。

**根因**：和 ko 一样——产物交接链 `内核 dist/ → device/qcom/kalama-kernel/kp-dtbs/ → dtbo.img` 中，`prepare_vendor.sh` 的搬运判断**只看 Image 在不在 + build.config 变没变，完全不看 dtbo 时间戳**。首次全编（8-20）铺了旧 kp-dtbs 后，后续增量编译内核正确重编了 overlay（dist 里是新的），但交接拷贝被跳过 → dtbo.img 一直用 8-20 的旧文件打包。

**修复**：改 DTS 后增量编译，必须先删 `device/qcom/kalama-kernel/Image`（和 ko 一模一样）——`dist/Image` 还在，**不会**引发内核重编，prepare_vendor 会秒级重铺 kp-dtbs + .ko + Image。

**铁律（统一版）**：任何内核改动（DT / defconfig / .c 源码 / .ko）做增量编译，**先删 `device/qcom/kalama-kernel/Image`**。不删 = prepare_vendor 不搬 = 产物全旧。

**验收**：编译后烧录前，用 `extract_dtbo.py` 验 dtbo.img 内容是否新（如 `boot-option` 是否已变）；或至少 `ls -la device/qcom/kalama-kernel/kp-dtbs/` 看时间戳。

### 坑 5：`=y` vs `=m` 决定 ko 到底存不存在 〔证据：build.sh MAKE_GOALS、prepare_vendor find 段；已实测 EXIT=0〕
GKI 架构下 msm-kernel 只 `MAKE_GOALS="modules dtbs"`，不链 vmlinux（Image 来自 common GKI）。
- vendor 驱动写 `=y` → **不产出 `.ko`**（built-in 无处可链，被 TRIM_UNUSED_MODULES 逻辑忽略）；
- `prepare_vendor` 的 `find dist/ -name *.ko` 扫不到它 → 进不了 vendor_dlkm → 刷机包无此驱动。
- 写 `=m` 才产 `.ko`，且 `vendor_dlkm.modules.load` 由 `find *.ko` 动态生成，编出来就自动收录。

→ **配置生效逻辑**（脚本 `build.config.msm.common` 中 `apply_defconfig_fragment` 实测，叠加顺序按行号走）：
```
gki_defconfig → kalama_GKI.config → consolidate_defconfig
               → consolidate.fragment → kalama_consolidate.config
               → vendor/kalama-consolidate_defconfig（最终锚点）
```
**三处都叠**（后写覆盖前写，但因为三处都是 `=m`，最终值不会变），不是"哪一处才是功臣"的关系。

- `kalama_GKI.config`：行 582-583 负责 `CONFIG_JOYSTICK_XONE_WIRED=m` + `CONFIG_JOYSTICK_XONE_WIRED_INPUT=m`；**行 588/590/591 还写了 CRYPTO_ECDSA/SHA256/HMAC=y**（built-in，进 GKI vmlinux 导出符号）；
- `kalama_consolidate.config`：行 33-34 冗余叠加同一组 `=m`（确保 consolidate 变体也有）；
- `kalama-consolidate_defconfig`：行 1398-1399 最终锚点。
**三者叠加，全部生效**——文档原说法"三处都要写 `=m`"是对的（坑 3 里写的符号依赖链另有机制，那是 modpost 阶段，不是"功臣归属"的问题）。

### 坑 6：软链树——改错目录就"改了不生效" 〔证据：readlink -f / stat inode 实测〕
`LA.VENDOR.15.4.3 → LA.VENDOR.15.4.3-irix`（QSSI 同理）。本次是软链、inode 相同，所以改哪都一样。
但历史上若存在两份**真实目录**（非软链），在 `.3` 里改配置、脚本却从 `.3-irix` 编，就会"明明改了没生效"。

→ **铁律**：动源码前 `readlink -f <路径>` 和 `stat -c '%i' <文件>` 确认你改的 = 编的那一棵。

### 坑 7：裸 `make defconfig` ≠ 脚本配置流程 〔证据：build.sh 用 merge_config 叠加 fragment〕
`build.sh` 的配置是 `defconfig` + `merge_config` 把 `${TARGET}.config`、fragment 叠上去。
手动 `make O=... defconfig` **只加载基础 defconfig，不叠加 vendor fragment**，于是 `XONE` 变回 "not set"，`scripts/mod/modpost` 也因没走 build.sh 的 `make scripts` 而缺失。

→ **铁律**：验证 vendor 驱动配置**不能**用裸 `make defconfig`，必须走 `build.sh`（或手动 merge 那些 fragment），否则得出"配置没生效"的假结论。

### 一条流水线看清全貌（ko 要真正进刷机包，缺一不可）
```
config =m（三个 config 文件都写，坑5）
  → build_kernel 产 .ko（走 build.sh，非裸 make，坑7）
  → dist/*.ko 新时间戳（坑2：别读残留）
  → build_kernel 产 dtbo（dist/ 里有新的）
  → prepare_vendor COPY_NEEDED=1（坑4：删 device Image 触发搬运）
  → find 搬进 device/qcom/kalama-kernel/vendor_dlkm/ 和 kp-dtbs/
  → make --target_only 打 vendor_dlkm.img → 进 super
  └─ 坑3：xone 依赖的 crypto 符号必须 GKI vmlinux 已编入，否则 insmod 仍失败
  └─ 坑4b：改了 DTS 后 dtbo 也必须搬，否则板上旧值（同一 COPY_NEEDED 门控）
```
任一环断，现象都是"编译没报错、板子上却没有"。

### 刷机后自检清单（替代"看着编完了就信"）
```bash
adb shell ls -l /vendor/lib/modules/xone*.ko          # ko 在不在
adb shell grep xone /vendor/lib/modules/modules.load   # 开机加载清单在不在
adb shell cat /sys/module/xone_wired/initstate 2>/dev/null # 已加载?
adb shell "dmesg | grep -iE 'xone|gip'"               # 有没有认领手柄
adb shell "dmesg | grep -iE 'Unknown symbol'"         # 坑3：是否因 GKI 缺符号才加载失败
# DT 改动后额外检查（VM 上，不用刷机）：
python3 /tmp/extract_dtbo.py <刷机包或dtbo.img路径> | grep -i kalamap-hdk   # 坑4b：DT 值是否已刷新
```
