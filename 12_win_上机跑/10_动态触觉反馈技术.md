## ⭐ 零基础导览:这个软件到底在干嘛(先看这篇!)

> 其他章节是"工程师版"细节;这一章是"白话版"。
> **看懂这一章,就能看懂全篇在讲什么。**

### ① 一句话总览

**电脑正在播放的声音,被我们"偷听"到 → 拆出里面的低音有多重
→ 换算成"该震多强" → 命令手柄马达按这个强度转。**

- 听声音 = `audio_capture.py`
- 拆低音 = `analyzer.py`
- 换算强度 = `analyzer.py`(内含映射)
- 命令马达 = `xinput_out.py`

### ② 声音是怎么一路"走到"手柄上的(流水线)

每 20 毫秒,下面这条流水线完整滚一圈,所以震动是**实时**跟着音乐的:

```
电脑在放歌(Chrome/游戏)
   ↓ ①WASAPI把一份声音悄悄复制给程序(0权限)
捕获:把声音切成 20ms 的小块(每块960个采样点)      ←【耳朵】
   ↓
FFT:把小段波形拆开,数一数"有哪些频率、各自多响"    ←【大脑】
   ↓ 只保留 30~130Hz 的低音(鼓/贝斯),其他丢弃
映射:把"低音多重"算成 0~1 的强度分                ←【翻译官】
   ↓ 乘 65535
输出:XInput 命令手柄马达转这么快                  ←【肌肉】
   ↓
手柄马达物理转动 → 你手心跟着鼓点跳动的震感
```

(旁边几个"配角"不在主链路上:`pipeline.py`=调度台、`ui/`=仪表盘、
`razer_probe.py`=侦察兵,详见附录B代码地图。)

### ③ 两个关键词:波形 = 振幅 + 频率

电脑里的声音就是**一条上下起伏的曲线**(波形)。它同时带两种信息:

| 词 | 白话解释 | 去向 |
|----|---------|------|
| **振幅** | 波形"跳多高" = **音量/力度** | ⇨ 变成马达转速(信息留下) |
| **频率** | 波形"抖多密" = **音调高低** | ⇨ **今天**只拿来"选段"用,筛完即弃 |

→ **振幅版(M0–M4)最重要的一句:**声音的两个维度,最后只有一个活下来;
频率只当筛子,振幅才是给马达的输入。

→ **频率版(W0–W5)要改的就是这句:**让频率也活下来,送给能变频的马达。
同事目标见「下一步」章。

### ④ 振幅 ⇌ 马达转速(一维的换算)

我们的手柄马达只有一个"旋钮":**转速 0 ~ 65535**。
- 低音能量大 → 转速高 → 震得强
- 低音能量小 → 转速低 → 震得弱
- 静音 → 转速归 0 → 不震

### ⑤ 为什么要"门限 + 压缩 + 增益"?(关键两步)

音乐里低音从"蚊子声"到"低音炮"跨度极大(0.02 ~ 1.2)。
直接给马达会两头吃亏:太强爆震、太弱没感觉。所以分三步"驯":

| 步骤 | 一句话 | 管什么 |
|------|-------|--------|
| **门限** 0.03 | 低于它就当没声音,转速=0 | 管**地板**:太安静不震 |
| **压缩** gamma=3 | 强音往下压、弱音相对抬 | 管**天花板**:不爆震,更均匀 |
| **增益** ×0.67 | 整体调一个舒服的音量档 | 管**档位**:留出强弱层次 |

口诀:**门限管多低才震,压缩管多高别爆,增益管整体定几档。**

### ⑥ 关键名词对照表(看到不懂的回来查)

| 名词 | 白话 |
|------|------|
| WASAPI 环回 | Windows 提供的"偷听线",能把系统正在播的声音复制一份给程序 |
| FFT(傅里叶) | 数学工具,把波形拆成"有多少 30Hz、多少 500Hz…" |
| ERM 马达 | 偏心转子震子，API 只有强度/转速；实际振动频率会随转速变，但与强度耦合，不能独立选 pitch |
| 宽频/高级触觉执行器 | 能呈现 pitch（低沉↔尖锐）的执行器。Wolverine 的具体结构官方未公开，不能先写死为 LRA |
| XInput | 微软的"电脑↔Xbox手柄"标准接口,`XInputSetState` 发振动 |
| 触觉 pitch / 输出频率 | Interhaptics 用 0–1 pitch + freqMin/freqMax 表示；设备如何实现仍待验证。**不等于**音频 30–130Hz |
| 频率窗 freq_win | 雷云日志里的时间常数;我们今天拿去平滑振幅,**不是音高** |
| ctypes | Python 调 C 接口的翻译工具(让我们能调 XInput) |
| 谱通量 | 业界标准的"检测节奏/鼓点"方法(动态模式用来打节拍) |
| 包络 | 让震感"起音快、收尾慢",像呼吸不神经质 |
| A2H | Audio-to-Haptics,音效转触觉,雷云 SENSA 的核心功能 |

## ⭐ 和雷云比,我们到底差在哪(2026-09-01 摸底)

**一句话:电脑这头的"翻译"我们已经和雷云用同一套数字;
手柄那头的"演奏",雷云是专业合成器,我们是拿音量旋钮在模拟。**

拆成五层看,每层状态一目了然:

| 层面 | 状态 | 白话 |
|------|------|------|
| ① 参数配方 | ✅ **追平** | 均衡模式与雷云一字不差(真值照搬) |
| ② 算法实现 | 🟡 **同类不同源** | 菜谱是对方的,锅是自己的 |
| ③ 输出硬件 | ❌ **XInput 天花板** | 不逆向绕不过去 |
| ④ 交互界面 | ✅ **基本对标** | 四档 1:1,卡片风格 |
| ⑤ 生态 | ❌ **短期没有** | Sensa HD 游戏源做不了 |

### ① 参数配方层:追平了

"什么声音触发多强的振动"这套映射,我们从雷云日志里挖出了完整配方,
均衡模式照搬,一字不差:

| 参数 | 雷云(日志真值) | 我们的均衡模式 |
|------|--------------|--------------|
| 采样 | 48kHz float32,周期 20ms | 相同 |
| FFT 窗口 | 50ms | 相同 |
| 输入频段 | 30-130Hz | 相同 |
| EQ 曲线 | 0Hz:1.0, 50Hz:1.0, 100Hz:0.3 | 相同 |
| 振幅窗/频率窗 | 40ms / 125ms | 相同 |
| 静音门限 | 0.03 | 相同 |
| 压缩器 gamma | 3 | 相同 |
| 触觉增益 | 0.67 | 相同 |
| 瞬态检测参数 | prominence 0.4 / 22ms | 相同 |

### ② 算法实现层:菜谱对了,锅是自己的

> **白话版(2026-09-03 补)**:
> 我们从雷云日志里挖到的是**参数**(盐放几克、火候多久),
> 不是**算法**(什么时候放、怎么翻)。雷云背后是
> **Interhaptics 编码器 DLL**(雷蛇收购的法国公司),源码不公开,
> 日志只吐数字、不吐公式。
> 所以我们不是"另搞了一套算法",而是**拿着同一份菜谱自己炒**,
> 手法必然跟对方不同——这就是标题说的"同类不同源"。
>
> 一个能摸到的后果:我们的压缩公式在能量超过 0.3 之后就削平了,
> 低音从 0.3 到 1.2 翻四倍,手上感觉完全一样(算术见下方"压缩器削顶")。
> 雷云多带一个 `amp_comp` 参数,很可能就是为处理这件事(软拐点,不是一刀切平)。

三处差异,全部落在 `analyzer.py`:

| 环节 | 雷云(黑盒) | 我们的实现 |
|------|------------|-----------|
| 节拍检测 | 公式未知 | 谱通量自研:`_detect_transient()` 取前后两帧频谱差,只统计 30-130Hz 的上升部分,超基线 8 倍即打拍,120ms 不应期。参数(prominence 0.4 / 22ms)对齐雷云,公式是自己想的 |
| 压缩器 | 有 `amp_comp 0.5`,**我们没实现** | 单一幂函数:`(能量 / 0.3) 的 1/gamma 次方`,gamma=3 |
| 输出形态 | "3 频段 + 2 瞬态点"的多通道触觉流 | **单一强度标量**,再人工拆成左右马达两个 0-65535 |

第三处最伤:雷云给马达的是一份"乐谱"(哪段频震多重 + 两个节拍点),
我们只剩一个"音量旋钮"。

#### 压缩器削顶(2026-09-03 实测算出来的)

公式:`压缩值 = min((能量 / 0.3) ** (1 / gamma), 1) × 增益 0.67`,gamma=3:

| 低音能量 | 输出到马达 |
|---------|-----------|
| 0.03(刚过门限) | 0.31 |
| 0.1 | 0.46 |
| 0.2 | 0.59 |
| **0.3** | **0.67(顶格)** |
| 0.5 | 0.67(顶格) |
| 1.2(低音炮) | 0.67(顶格) |

**能量过 0.3 后全部削平** → 中等音量以上的鼓点强弱层次全丢,
这解释了实测数据里三档峰值都卡在 0.5~0.67 同一个天花板上。
补 `amp_comp`(软拐点)或抬高参考值 REF_LEVEL 都能缓解,属于低成本可补项。

### ③ 输出硬件层:差距最大,也是本质区别

| | 雷云 | 我们 |
|---|------|------|
| 通道 | 雷云私有驱动 + HID | 标准 XInput API |
| 马达控制 | Interhaptics 层有 amplitude + pitch + freqMin/freqMax；设备报告曾见频率范围，底层实现待验证 | 双马达**强度/转速 0-65535**；物理频率可能跟转速变化，但不能和强度解耦 |
| 扳机马达 | 能控(Pro HyperTrigger) | 控不到 |

打个比方:雷云/Interhaptics 能描述「同样力度、不同 pitch」,
像专业合成器分别调音高和力度;我们只能调"转速高点儿/低点儿"，强弱与物理频率绑在一起，
颗粒度粗。这不是我们没写好,是 **XInput 公开接口只有转速这一个旋钮**,
公开 XInput 绕不过去。

想追平这条路,不能再只调 `analyzer.py` 的增益。
同事已定方向:**先摸透雷云怎么控频率,再把我们的 Windows 雷云做成能发频率的。**
优先尝试官方公开的 Interhaptics/Wyvrn 参数化接口；公开接口走不通，才逆向设备输出。
完整步骤见下一章;抓包细节见附录 D。

### ④ 交互界面层:基本对标

- 四档位(受控/均衡/动态/自订)与雷云官方
  CONTROLLED/BALANCED/DYNAMIC/CUSTOM **1:1 对应**,不是自创
- 触觉源两卡(音效转触觉 / Sensa HD 游戏置灰)、档位卡片、
  频段增益拖拽编辑器,都对齐了雷云 SENSA HD 的页面结构
  (官方 DevKit 截图考证,截图存在 `25_xbox_control\_razer_ui_ref\`)
- 剩的差距主要是"精致度":动画、字体渲染细节、多语言这些皮毛

### ⑤ 生态层:短期做不了

雷云的 Sensa HD **游戏源**需要游戏接 Interhaptics SDK、主动输出触觉流。
我们抓不到游戏内部数据,这条路走不了;我们做的是**音效转触觉**这一源
(把系统声音翻译成振动),对任何游戏/音乐/视频都生效——
其实这反而是我们的一个优势:**雷云只在支持的游戏里震,我们什么都震**。

### 一个要诚实说明的点:四档之间的差异,是我们设计的

雷云日志里只有**一份**引擎配方快照,四档各自的内部差异**从未写进日志**。
所以:

- 均衡 = 真值原样落地 ✅
- 受控/动态 = 我们在均衡基础上按"更克制/更猛"方向**自己设计的变体**
  (门限 0.04/0.02、gamma 3.5/4.0 这些偏移量没有雷云依据)
- 瞬态音量 0.25/0.35/0.6、各档频段增益曲线,同样按实测手感调的
  (日志快照里瞬态音量甚至是 0——但实测全关瞬态手感很差,说明雷云在
  引擎层另有机制,我们只能用手感反推)

方向肯定是对的(克制↔均衡↔猛烈),但**别指望三档间的手感比例
和雷云完全一致**——这个没有可抄的答案,只能实测反馈慢慢磨。

## ⭐ 下一步:摸透雷云频率,做出能控频的 Windows 雷云(2026-09-14)

> 同事原话:**先把雷云的频率摸透,把我们的 Win 雷云做出来,至少能知道怎么控制频率。**
> 这一章就是按这个目的写的方案。振幅版(M0–M4)保留,不推倒重来。

### 0. 目的、验收、这阶段不做什么

**目的一句话:**搞清楚雷云怎么把「音高」送到马达,再让我们的 Windows HapticX 也能发 `频率 + 振幅`,而不只是转速。

**先说结论边界:**这两份文档是一条可验证、可停损的研发路线，**不是已经证明一定能让这只手柄唱歌**。
最终能否直控取决于至少一条成立：

1. 官方 Interhaptics/Wyvrn 运行时允许第三方程序把 amplitude + pitch 发到 Wolverine；
2. 或者能从 USB/驱动输出中还原并合法复述设备协议；
3. 两条都不成立时，只能换成有公开频率接口的执行器，不能靠继续调 XInput 实现。

**验收(都过才算 Win 雷云频率版做出来了):**

| # | 过关标准 | 没过长什么样 |
|---|---------|-------------|
| A | 同一力度、换音高,手上能分出「低沉 / 尖细」(小星星那种) | 只有强弱,没有音阶 |
| B | 我们的程序能生成 `A=0~1` + `pitch=0~1` + `freqMin/freqMax`（需要时换算显示 Hz） | 仍然只有左右两个 0–65535 |
| C | 命令真正进了能变频的马达(这只雷蛇的 LRA,或一块实验用 LRA) | 频率只写在屏幕上,手柄还是 ERM 嗡嗡 |

**这阶段明确不做:**

- 不刷安卓、不改 A2DP / `ff_bridge`、不装掌机 Switch 马达
- 不把 Steam Controller / DualSense / Joy-Con 当产品目标(最多当「能变频的实验台」)
- 不抓 HapticX 的 `XInputSetState` 当答案——那个包我们会了,里面没有频率
- 不跟雷云抢马达:抓包和听诊时 **只开一边**

### 1. 三个「频率」别混(先读,否则后面全错)

文档和代码里至少有三种东西都叫频率,只有第三种是同事要的:

| 名字 | 它到底是什么 | 我们今天 | 同事要的? |
|------|-------------|---------|----------|
| **① 音频频率** | 声音里 30–130Hz 的鼓/贝斯 | FFT 当筛子,筛完丢掉 | 否(已经会) |
| **② `frequency_window_length`** | 雷云日志里的 **时间常数**(均衡档 125ms) | `analyzer.py` 的 `_frequency_smooth()` 拿它去 **再平滑振幅** | 否。**名实不符**,不是马达音高 |
| **③ 触觉 pitch / 输出频率** | 官方 API 用归一化 pitch 描述低沉↔尖锐，并给 freqMin/freqMax；硬件可能是波形、固定频带或多执行器映射 | **完全没有。XInput 带不走** | **是** |

所以「摸透频率」不是再调一遍 30–130Hz 的 EQ,而是回答三句人话:

1. 雷云听到一段声音后，生成的 **pitch 曲线是怎么来的**？（跟音频主频、频谱质心还是频带能量走？）
2. 能否通过官方 `AddParametricEffect` / `.haps` 路线直接给 amplitude、pitch、freqMin、freqMax？
3. 若只能逆向，设备侧输出是显式频率字段、归一化 pitch、固定频带振幅，还是编码后的波形/分块？

### 2. 为什么现有 Win 雷云唱不出小星星

```
真雷云:   声音 → Interhaptics 编码器 → 设备适配层 → 高级触觉执行器 (振幅 + pitch + 多通道)
我们今天: 声音 → analyzer.py        → XInput    → 标准 rumble      (只剩 0–65535)
```

- **标准 XInput rumble:**接口只给左右强度/转速，不提供独立 pitch；转速变化可能带来物理频率变化，但不能保持同强度单独换音高。
- **SENSA 高级触觉:**官方 Interhaptics 表示层支持 amplitude 与归一化 pitch；Wolverine 内部执行器类型和协议编码尚未实证。

这只手柄是 **Razer 1532:0a3f**(无线收发器 / 有线同 PID)。雷云手感更细，说明存在 XInput 之外的高级触觉路径；
**但这不能单独证明它是 LRA，也不能证明 USB 包里有一个直接等于 Hz 的字段。**
微软公开的 XInput **故意不暴露** 这一维。安卓 `FF_RUMBLE` 是同一天花板。
掌机以后若改装 LRA,用的就是这里摸出来的「F + A 怎么控」,所以 **必须先在 Windows 上做完**。

#### W3B · USBPcap:公开接口不通时才逆向

环境(已踩过的坑,照做):

- USBPcap 1.5.4 已装。`\\Device\\USBPcapN` **只在开机挂栈时出现**
- **抓之前重启一次电脑。禁止 `pnputil` 热重绑控制器**(`pcap_setup.ps1` 里的 disable/enable 会把 USBPcapN 弄没,不要跑那一段)
- VMware 的 `hcmon` 会跟 USBPcap 抢过滤器;抓包时尽量别开虚拟机 USB 穿透
- 脚本和 pcap 只放纯英文路径:`D:\win_game_project\13_win_cap\captures\`
- 手柄用 **0a3f**(雷云 SENSA 那套人格)。切到 0a4c PC 模式可能只剩 XInput 转速,频率通道会丢

**抓取时不要只抓 Interrupt，也不要用 VID/PID 过滤后保存。** 后续 URB 往往不重复携带
`usb.idVendor/idProduct`。先抓整个 Root Hub，插拔/枚举时从描述符找到 1532:0a3f
对应的 `usb.bus_id` + `usb.device_address`，之后用地址过滤全部 control/bulk/interrupt OUT。

USBPcap/Wireshark 的 transfer type：

```
usb.transfer_type == 1    # Interrupt
usb.transfer_type == 2    # Control，不是 Interrupt
usb.endpoint_address.direction == 0   # OUT；1 是 IN
```

定位设备后推荐显示过滤：

```
usb.bus_id == <bus> && usb.device_address == <addr> &&
usb.endpoint_address.direction == 0
```

保留所有 endpoint 与 transfer type。不要只盯当初 rumble 的 ep——高级触觉可能走
control、bulk、interrupt、分块流或固定频带振幅，不一定存在一个显式 Hz 字节。

| 文件 | 你做什么 | 这个包代表什么 |
|------|----------|----------------|
| `F50_sensa.pcapng` | 只开 SENSA,放 `tone_050.wav` 8s | 谐振点的「原话」 |
| `F110_sensa.pcapng` | 同上,`tone_110.wav`,响度对齐 | **和 F50 比,哪几个字节变了 = 频率字段** |
| `F200_sensa.pcapng` | 同上,`tone_200.wav` | 超输入带时还变不变频 |
| `STAR_sensa.pcapng` | 同上,`star.wav` | 音阶序列是否在包里逐音出现 |
| `SILENT_sensa.pcapng` | SENSA 仍开,静音 10s,手别动 | 心跳 / 保活,不是音乐 |
| `XINPUT_hapticx.pcapng` | 关 SENSA,开 HapticX 放同一条 50Hz | 对照:只有转速,没有 F |

分析(pcap 交给 AI 即可,不必会 Wireshark):

1. 至少做 `3 个输入频率 × 3 个响度` 的因子实验，不能只比 F50/F110 两份；
2. 随输入频率单调变化、且在三档响度下规律一致的字段，才是 pitch **候选**；
3. 随响度单调变化、且在三种频率下规律一致的字段，才是 amplitude **候选**；
4. SILENT 里仍在发、演奏时多出来的 → 保活 vs 演奏；
5. XINPUT 包对得上我们已知的 GIP rumble(13 字节那类)→ 证明「我们的话」和「雷云的话」不是同一种。

候选模型还必须拿**未参与建模的频率/响度**交叉验证。可能没有单字节频率字段，
而是归一化 pitch、查表索引、多个固定频带强度或编码波形。验证前不能把“相关”写成“协议”。

| 动态 | 0.42 → 0.67 | +0.25 | +0.39 | 48/48 |

四档峰值输出同一量级(0.5-0.67),差异体现在弹跳力度——
这是刻意的:档位差异应该在"手感",不在"绝对音量"。

## 修过的坑(按时间线,每条:现象 → 根因 → 修法)

**2026-08-31 · 压缩器归一化用错分母**
- 现象:四档输出差 3-4 倍,受控几乎没感
- 根因:归一化分母写成了 `gate * 10`,各档 gate 不同 → 输出跟着 gate 漂
- 修法:固定参考值 0.3,所有档位同一起跑线

**2026-08-31 · 节拍检测超触发**
- 现象:86 次触发(理论 20),镲片/衰减尾都算一拍
- 根因:谱通量统计了全频段,且无不应期
- 修法:只统计 30-130Hz + 120ms 不应期 → 36 次

**2026-08-31 · 频段增益不随档位切换**
- 现象:点档位手感变了,增益柱纹丝不动
- 根因:四档共用一份全局 band_gains
- 修法:每档一条曲线(MODE_BAND_GAINS),切档时画布同步刷新,
  拖拽只写当前档的存档 `mode_band_gains[档]`,旧配置自动迁移

**2026-09-01 · 均衡/受控完全不弹(用户实测反馈)**
- 现象:这两档左右马达稳稳嗡着,没节拍弹跳
- 根因:两档 `transient_vol=0`,瞬态检测直接短路;
  右马达公式 = 瞬态 + 低频×0.4,瞬态没了右马达天然只剩四成
- 修法:四档瞬态全开(0.25/0.35/0.6),梯度保留

**2026-09-01 · 瞬态脉冲"触发即衰减"**
- 现象:节拍弹跳力度普遍偏弱,不到设计值一半
- 根因:`transient_amp` 刚置满幅,同一个 20ms 块内就被乘 0.4 衰减,
  相当于还没出手先挨一刀
- 修法:`_transient_fresh` 标志——触发块满幅输出,下一块起再按
  22ms 时间常数衰减

**2026-09-01 · 雷云 UI 结构认错(用户反馈"雷云只有绿蓝两档")**
- 现象:把官方四预设当成了我们自创,把"绿蓝两档"当矛盾
- 根因:没考证雷云 SENSA HD 页面真实结构
- 修法:拉官方 DevKit 截图确认——**Haptic Source 两卡**(音效转触觉绿 /
  Sensa HD 游戏蓝)+ **A2H PROFILE 四预设**,四档 1:1 是对的;
  补做了触觉源两卡,整个页面重构成雷云卡片风格

**环境坑(记下备查)**
- TRAE 精简版 python 无 tkinter → 装完整 Python 3.13 到用户目录
- 沙箱拦截往 Python 安装目录写 .pyc → GUI 用 `-B` 启动

- 均衡 = 配方快照原样落地;受控/动态 = 均衡上自设计的变体;

- 设置页六滑条(gate/band_scale/gamma/transient_vol/freq_win/amp_win)
  一一对应雷云配方 JSON 的真实字段,初值即快照值
- 勘误:此前文档写"雷云瞬态常开"系推断,实际快照里

## 附录 C:关键实现细节

### 音频捕获(soundcard)

```python
import soundcard as sc
mic = sc.get_microphone(id=str(sc.default_speaker().name),
                        include_loopback=True)
# record(blocksize=960) → 48kHz float32,混音后的系统全部声音
```
- soundcard 的 loopback 即 WASAPI 环回,免虚拟声卡、免管理员权限
- 960 样本/块 = 20ms(与雷云采集周期一致)

### FFT 分析(numpy)

- `np.fft.rfft`,2400 点窗(50ms,同雷云),20ms 步进
- 单频段 30-130Hz × EQ 曲线(四关键帧线性插值)
- 频段增益编辑器实时重建 eq_table

### 双马达映射

- 左马达 = 频段电平 + 瞬态×0.7(主力:低频稳态+节拍)
- 右马达 = 瞬态 + 频段电平×0.4(主力:节拍弹跳)
- 50Hz 输出;`XInputGetState` 探测断连,断连即停发
- 左右都是振幅。UI 把右马达标成「高频」只是「节拍更尖」,**不是马达 Hz**
- `_frequency_smooth()` 用的 `freq_win` 是第二趟振幅平滑,见附录 A 勘误

```python
import ctypes
xinput = ctypes.windll.xinput1_4
class VIB(ctypes.Structure):
    _fields_ = [("l", ctypes.c_ushort), ("r", ctypes.c_ushort)]
# VIB(左0-65535, 右0-65535) → XInputSetState(0, byref(v))
```

- 流程:雷云里**关闭 SENSA 动态触觉** → 启动本程序 → 放歌即振
- 雷云可常驻,启动时检测到进程弹提醒(不强制杀)
