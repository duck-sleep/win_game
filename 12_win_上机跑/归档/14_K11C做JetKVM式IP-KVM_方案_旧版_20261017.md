# 上半部分 · 给人读

## 1.1 这一版到底要证明什么（2026-10-16 你拍的板，目标已收缩）

**一句话**：先把板子调通 —— **插到你笔记本上，Windows 把它当成一副键鼠，真的能打出字**；
同时浏览器里能看到一个画面。**被控机就是你现在这台 Windows 笔记本，不装任何东西。**

只有两个验收问题：

| # | 要证明的事 | 怎么算过 |
|---|---|---|
| **①** | 板子能对被控机当键盘+鼠标 | Windows 设备管理器出现新键盘/鼠标，**记事本里真的打出字、光标真的动** |
| **②** | 浏览器能看到画面（先假源） | 笔记本浏览器打开板子地址，看到那张图**且图上的毫秒表在走** |

**现在做**：内核开 HID gadget → ACM 探针 → 插笔记本打字 → 配 WiFi → 假源上浏览器 → 移植 JetKVM 的控制页。
**现在不做**（都推迟，架构留着，不是砍掉）：

| 不做 | 为什么 | 什么时候回头 |
|---|---|---|
| 在被控机装 agent 推屏 | 你说"先别装怪东西"，先把板子调通 | ①②都过了之后 |
| 采集棒 / HDMI 输入 | 被控机就是笔记本，不需要在"没系统"时看它 | 真要进 BIOS 那天 |
| 安全 / 鉴权 | 你说不管；且被控机是你自己的笔记本、家里内网 | 哪天要出门用/给别人用 |
| 继电器远程开机、多台被控机 | 单台、开着的笔记本，用不上 | 需要时（纯硬件/纯扩展） |
| HDMI out 接显示器 | 前期不接 | 你以后想接就接（见 §2-Q12 的注意事项） |

### 1.2-A 最终形态（推迟，先记着）

```
被控机 agent（截屏→编码→带时间戳推流）──WiFi──► 板子（转发）──WiFi──► 浏览器
```

### 1.2-B′ 这一版主动放弃了什么（诚实记录）

- **看不见 BIOS / 蓝屏 / 重装**：画面来自软件，被控机没系统就没画面 —— 你明确说**不需要**。
- **不能远程开机**：继电器不接，机器关死了只能人去按 —— 你说被控机**一直开着**，成立。
- **不安全**：局域网里谁能访问那个地址，谁就能替你敲键盘 —— 你说**不管**。
  （记一句：JetKVM 有 `local_loopback`/TLS/OIDC 这些开关，将来要补随时能补，见 §2-Q17。）

## 哪些"用不了就算了"，哪些一挂就全挂

你这个直觉是对的：**搬过来的软件几乎全属于"用不了就算了"**。但有一层不是软件搬运能兜底的。

| 层 | 东西 | 挂了会怎样 | 现在状态 |
|---|---|---|---|
| **地基** | ① Type-C 真能当 device（UDC 出现） | **全盘 0 分**：板子不是外设，没有 KVM | ✅ 已写死 `dr_mode="peripheral"`，待板上确认 |
| **地基** | ② 内核有 HID gadget | **全盘 0 分**：没有键盘这个功能 | ✅ 已编进 boot.img，待烧 |
| **地基** | ③ **Windows 认我们的 HID descriptor** | **全盘 0 分**：枚举不出键鼠，后面全免谈 | ❓ **唯一"必须上板才知道"的一条**；但我们照抄的是它在同类 DWC3 上验证过的字节表，风险已压低 |
| 备胎 | ④ WiFi 拿到 IP | 看不到画面、进不去板子 | ⚠️ 不通有网线兜底，不是死路 |
| 可丢 | JetKVM 前端 `ui/`（160 个文件） | 界面丑一点，功能不减 | 随时可放弃，自己写 60 行页面即可 |
| 可丢 | WebRTC 那 1332 行 | 延迟高一点、码率大一点 | 用 MJPEG 就行 |
| 可丢 | 它 118 个 RPC 方法里的 110 个 | 少一些花活（云、虚拟媒体、MQTT、扩展） | 只实现 8 个就够跑 |
| **半可丢** | 键盘布局表 `keyboardLayouts/*` + `useKeyboard.ts` | 中文/异体键盘会难用 | **这个最值得搬** —— 不是"好看"，是"自己写要踩一周坑"的部分 |
| 可丢 | 画面本身 | **看不见但键鼠仍然能用** | 极端情况下砍掉画面，这仍然是一台"远程键鼠" |

⇒ 一句话：**画面是体验层，键鼠是能力层**；能力层只有 ①②③ 三条，其中 ①② 已经做完，
**③ 是这次烧写要回答的唯一问题**。所以"搬过来用不了就算了"对软件层成立，对 ①②③ 不成立。

## 一个必须先说清的前提：GPL

你说"JetKVM 怎么实现就怎么实现" —— 它的固件与前端是 **GPL-2.0**。
- **自己用、不分发** ⇒ 随便抄，没有任何义务公开，**我们现在的场景就是这种**；
- **哪天要公开/分发/卖** ⇒ 抄过改过的部分必须同样按 GPL 开源（PiKVM 更是 GPL-3.0，别混用）。
所以"照抄"这条路我按你说的执行，只是把这条边界写在纸上，别将来被动。

# 二、逐条展开

## Q1 哪个物理座接在哪个 USB 控制器上（OTG / SuperSpeed）🟢 基本已答，待板上确认

### 板子实际有几个口（已证，两处独立来源）

**官方文档原文**（外设接口节）：
> 「K11C 具备 **1 个 USB 3.0 端口和 1 个 USB 2.0 端口**，可以使用任意 USB 端口连接键盘和鼠标。」
> 「通过 **USB TYPE-C** 将镜像安装至主板 eMMC 中」

**机械图 DXF 里的件号/网络名**（`K11C_V1.2_20260811.dxf` 的 TEXT 实体直接可读）：
`TYPE-C`、🔴 **`TYPE-C_OTG`**、`CS-USB30-AF-U321`（USB3.0 A 母座）、`USB2.0`、`USB3.0`

→ 物理形态 = **1× Type-C（丝印/网络名就写着 OTG）+ 1× USB3.0 A + 1× USB2.0 A**，与实物一致。

### SoC 侧有**四条** USB 通路（读 `rk356x.dtsi` 实测）

| 控制器 | 地址 | 能力 | 推测对应的物理座 |
|---|---|---|---|
| `usbdrd_dwc3` | `fcc00000` | `dr_mode="otg"`，USB3 DRD | **Type-C（`TYPE-C_OTG`）** |
| `usbhost_dwc3` | `fd000000` | `dr_mode="host"`，**SuperSpeed**（`combphy1_usq PHY_TYPE_USB3` + `u2phy0_host`） | **USB3.0 A 座** |
| `usb_host0_ehci/ohci` | `fd800000` / `fd840000` | 纯 USB2 host（`u2phy1_otg`） | **USB2.0 A 座** |
| `usb_host1_ehci/ohci` | `fd880000` / `fd8c0000` | 纯 USB2 host（`u2phy1_host`） | 备用/未引出 |

### 🔴 之前担心的"最坏情况"不成立

原以为可能出现"唯一的 USB3 座恰好就是 OTG 口，视频要 3.0 与 HID 要 device 抢一个座"。
现在看：**Type-C 是 DRD（可做 device），而 USB3.0 A 座是独立的一条 host + SuperSpeed 通路** ——
**HID 走 Type-C；两个 A 座在定稿里空着**（它们本来是为采集棒准备的）。

> ⚠️ **这条结论现在的价值变了，但别删**：不买采集棒之后，"USB3 到底在哪个座"**不再是架构前提**，
> 只剩两个用途：① 万一将来回头做档 3，直接照这张表插；② **它仍然是 Q2 的交叉验证**——
> 插线时看哪个控制器出现 UDC，就能证明 Type-C 真的接在 `fcc00000` 上。所以 P1.5 顺手填表，成本几乎为零。

### 已经算被实证的一半

**烧录那次就是 device 角色**：官方文档写「通过 USB TYPE-C 将镜像安装至 eMMC」，
进 MASKROM/LOADER 时板子就是挂在 Windows 上的 **USB device** ——
而我们昨天正是这么把自编固件刷进去的。
→ **Type-C 的数据线通到 device-capable 控制器**这件事已被物理证明（BootROM device 模式与 Linux gadget 走同一套 D+/D- 与角色硬件）。

### 剩下的未知（缩到很小，且都是运行时问题）

1. Linux 下 `dwc3` 有没有真把 UDC 注册出来（多半有，因为 adb/gadget 类功能在别的 RK 板上同理会通）；
2. Type-C 的 **CC 有没有配电阻/ID 怎么接** —— 决定插上是被控机还是板子当 host、要不要 sysfs 强制；
3. USB3.0 A 座是否真落在 `fd000000`（SuperSpeed 那一路）—— 若实际在 ehci 上，采集棒就只有 USB2 带宽。

**一次实测全结掉**（P2 时做）：
```bash
ls -l /sys/class/udc/                    # 只有 DRD 控制器会出现 UDC
for u in /sys/class/udc/*; do echo "$(basename $u) state=$(cat $u/state) speed=$(cat $u/current_speed)"; done
dmesg | grep -iE "dwc3|xhci|new .*(high|full|super)-speed USB device"   # 采集棒分别插两个 A 座各试一次
cat /sys/class/typec/*/data_role 2>/dev/null                            # 顺带答 Q2
```
**判据**：填出这张表就结题 —— `物理座 | 控制器 | SuperSpeed? | 能否 device`。
**万一 USB3 不在 A 座上**：⚪ 已无关 —— 采集棒不买了（定档 2），这条只影响"将来回头做档 3"时的画质上限。

## Q2 Type-C 的角色怎么决定 🟢 已答：写死 `dr_mode="peripheral"`

**结论（你的提法就是最终设计）**：Type-C 强制 device → 电脑做 host → 板子在被控机眼里就是一个键盘+鼠标。
不需要 PD、不需要 CC 协商、不需要 OTG 检测。

**为什么会不确定**：本板 dtsi 里 **usb/typec/dwc3 覆盖 0 命中** → 吃的是 SoC 默认 `dr_mode = "otg"`。
otg 模式下角色要 PHY 去看 VBUS/ID，而 Type-C 座上没有 CC 控制器（DXF 里只有 `TYPE-C_OTG` 网络名）
→ 插上去到底进哪个角色，**没人保证**。这就是 Q2 不确定性的全部来源。

**✅ 已实装（2026-10-16，不再"先判后改"）**：直接改了 dts。理由是**读源码 + 读编译出的 DTB**就能定，不用花一次烧写去试：

| 证据 | 结论 |
|---|---|
| `dtc -I dtb -O dts` 看**实际编译进板子的 DTB**：`/usbdrd/usb@fcc00000` 是 `status="okay"`、`dr_mode="otg"`、`phy-names="usb2-phy"`，**全 DTB 里 `usb-role-switch` 出现 0 次、也没有 `extcon`** | 角色没有任何硬件/固件通道去告诉 DWC3 |
| `drivers/usb/dwc3/drd.c:564 dwc3_drd_init()`：有 `usb-role-switch` 才走 role switch；有 `edev` 才走 extcon；**否则落到 `else` 分支 → `PRTCAP_OTG` + 抢 OTG ID 中断** | 我们正是第三种：角色由 **ID 引脚**决定 |
| `drivers/usb/dwc3/core.c` 的模式分支：`USB_DR_MODE_PERIPHERAL` → **无条件 `dwc3_gadget_init()`** | 写死 peripheral ⇒ UDC 必然注册，不再有"会不会出现"的问题 |

⇒ 本板 Type-C 没有 CC 控制器（DXF 只有 `TYPE-C_OTG` 网络名），ID 悬空时 DWC3 大概率停在 host ⇒ **UDC 可能压根不出现**。
所以这不是"优化"，是把一个 50/50 变成 100%。

**改了什么（全量 diff 就 2 个文件 8 行）**：
```
kernel-6.1/arch/arm64/configs/rockchip_linux_defconfig        | 1 +   CONFIG_USB_CONFIGFS_F_HID=y
kernel-6.1/arch/arm64/boot/dts/rockchip/rk3566-kickpi-k11c-v12.dtsi | 7 +   &usbdrd_dwc3 { dr_mode = "peripheral"; };
```
⚠️ **改内核 config 必须改 defconfig，不能改 `.config`** —— `mk-kernel.sh` 的 `do_make_kernel_config()`
每次构建都跑 `make $RK_KERNEL_CFG`（= `rockchip_linux_defconfig`）**重新生成 .config**，手改 `.config` 会被无声覆盖。

**代价**：Type-C 从此不能当 host。用不上（两个 A 座才是 host 口，而且现在连采集棒都不买了）。
烧录不受影响：MASKROM/LOADER 由 ROM/U-Boot 设 device，**不读 Linux 的 dts**（⚠️ 仍是推理，未证 —— 但这次烧写本身就会验证它：如果烧不进去，说明这条推理错了）。

**注意这条不等于"键盘就有了"**：强制 device 只解决"USB 层谁是 host"，
还要 **Q3**（内核 HID gadget，现在缺）和 **Q10**（configfs 里的 report descriptor 要含绝对坐标指针）。

> **供电（=Q9 的另一面）**：device 按规范应从 host 取 5V，但被控机 BIOS 阶段可能限流甚至不给，
> 而 KVM 必须常在线 → **板子用原装电源独立供电，Type-C 线只走数据**。
> 顺手确认 GND 共地、别出现两头都灌电的回路。

## Q4 视频入：**三档**可选（假源 / 被控机推屏 / 采集棒）🟡（2026-10-16 因"能不能去掉采集棒"重开）

### 先补一张三档对照表（你提的"去掉采集棒"= 用第 2 档替第 3 档）

| 档 | 画面从哪来 | 能看到什么 | **看不到什么** | 成本 | 时间戳 |
|---|---|---|---|---|---|
| **1 假源** | 板子自己生成（一张图 + drawtext） | 只有那张图 | **全是假的** —— 只能证"编码→网络→浏览器"这条链路 | 0 | 只能烧进像素，靠**拍屏**量 |
| **2 被控机推屏**（agent） | PC 上跑一个程序，把自己的桌面推到板子 | **真实 Windows 桌面**，画质/帧率最高、延迟最低 | 🔴 **BIOS/UEFI、开机自检、PE、蓝屏、重装系统、agent 没起来的一切** | 0（要写/装一个 agent） | ✅ **帧里直接带生成时间戳** → 端到端延迟能算出来，不用拍屏 |

**关键取舍（这条决定它是不是 KVM）**：档 2 能覆盖的场合 = "被控机已经开着、装着软件、能上网"——
**那种场合你本来就有 RustDesk/向日葵可用，不需要这块板子**。
KVM 的价值恰恰落在**档 2 瞎掉的那些时刻**：进 BIOS 改启动项、系统蓝屏进不去、重装、被控机没网、agent 忘了装。
⇒ **采集棒不是"能不能省"的问题，它决定这台东西是"KVM"还是"远程桌面中继"。**

**但你的提议仍然值得采纳一半**（而且 JetKVM 自己就是这么分层的）：
- **P5 那笔钱先不花**：档 1 跑通链路之后，**直接做档 2** —— 零成本拿到**真画面 + 真时间戳**，比等采集棒到货还快；
- 档 3 推到"**我真的要在没有操作系统的时候操作它**"那天再买（架构不用改，只是把源从 agent 换成 `/dev/video0`）。
- 对照 JetKVM：硬件采集是产品本体，另外单独出 "**JetKVM OS Services**"（在被控机里跑，可采到 4K、共享剪贴板、guest 终端、文件传输）
  → **软件增强和硬件采集是并存关系，不是互相替代**（§3.1 已核）。

⚠️ **档 2 的时间戳有个真坑**：两端时钟不同步，算出来的延迟就是假的（板子和 PC 差几秒很常见）。
要么两边都跑 NTP/chrony 并测一次 offset，要么**保留"拍屏读毫秒表"这个物理量法当校准**。

### 硬件层已证的事实（这几条不变）

**已证 K11C 没有 HDMI 输入**：

## Q5 ⚪**已关闭**：采集棒规格与延迟（2026-10-16 决定**不买**）

> **为什么还留着这一节**：万一哪天要"在没有操作系统的时候操作被控机"（进 BIOS / 重装 / 救蓝屏），
> 这一节的选型与实测方法是现成的，**届时直接启用，架构不用改**（只是把画面来源从 agent 换成 `/dev/video0`）。
> 平时可以整节跳过。

### 采集棒到底是个什么东西（一句话讲透，给第一次接触的人）

**外形**：一个 U 盘大小的东西，**一头是 HDMI 母口，另一头是 USB 插头**（有的带一根短 USB 线），
淘宝搜"HDMI 采集棒"，芯片认 MacroSilicon **MS2109 / MS2130**，**几十块钱，不用驱动、不用供电、不用焊**。

**它干的活**：把"HDMI 那头的画面"变成一个"**USB 摄像头**"。
插到板子上，`/dev/video0` 就出现了 —— 板子以为自己在看一个摄像头，其实那颗"镜头"看到的是**被控机的屏幕**。

**为什么非它不可**：板子的 HDMI 口是**输出**（TX），**全板没有任何 HDMI 输入**（§2-Q4 已证：DTS 里没有 `hdmirx` 节点）。
所以"把 PC 的画面线直接插到板子上"这条路**物理上不存在**，必须有个东西做 **HDMI → USB 的翻译**。
（另一条翻译路线是 HDMI→MIPI 桥，要画板/飞线/写驱动 —— 见 Q4，我们不选。）

**方向别买反**：要 **HDMI → USB（采集）**，不是 **USB → HDMI（转接头/DisplayLink，那是往外输出画面的）**，
两者长得几乎一样，插上去什么都采不到。

### 选型与实测

**现在没有任何数据**，别拿厂商标称当真。选型要点：
- 🔴 **方向别买反**（理由见上面那段）；搜索关键词认"**HDMI 采集卡/采集棒 UVC**"。
- USB2 带宽天花板：1080p30 只能走 **MJPEG**，YUY2 只能到 720p —— 这直接决定延迟与画质
- **已证 host 控制器带 USB3**（`combphy1_usq PHY_TYPE_USB3`）→ 若采集棒是 MS2130 且**插到的物理座真是 USB3**，
  可争取 1080p60；前提是 Q1 那张表填出来对口

**实测方法**（⚪ 已关闭；若将来回头买采集棒再做，判据写死如下）：
```bash

# 延迟用物理量法：拍被控机屏幕上的毫秒表，同时看采集端收到的时间戳，两边相减
# —— 这才是"采集段"延迟，与假源阶段量到的"编码+网络+浏览器"是两段，分开报
```
**判据**：拿到「分辨率 / 帧率 / 格式 / 端到端延迟」四个真实数字，再决定 Q4 要不要返工。
预期管理：**JetKVM 标的 30–60ms 是 MIPI+硬编路线，USB 棒达不到**；
而且连 JetKVM 自己的低端款 Mini 也只是 **1080p30 / 720p60**（§3.1 已核）→
**届时做到 1080p30 就该算达标**，别拿 1080p60 当基线。

## Q6 `rockchip.service` 为什么 failed 🟠

板上现在还在 failed。它是"Setup rockchip platform environment"，**很可能在配 MPP/RGA/VPU 的权限与 udev 规则** ——

更深一层的怀疑（**未证**）：我们的 rootfs 是从官方成品 img overlay 来的，服务里的脚本可能假设了
官方内核的模块布局，而我们编的内核没把那 156 个 `.ko` 投进去（见 Q7）。**这可能就是它 failed 的原因。**

**怎么查**（板上，我现在就能做）：
```bash
systemctl status rockchip.service --no-pager
journalctl -u rockchip.service --no-pager | tail -40
systemctl cat rockchip.service | head -30
```
**判据**：知道失败点，并判断它是"无害跳过"还是"砍掉了硬编能力"。

## Q7 自编模块怎么进 rootfs 🟠

**已证**：板上 `/lib/modules` 是**平铺的 10 个厂商 `.ko`**（bcmdhd / skw* / swt6621* / hci_uart / rtk_btusb），
**没有 `6.1.141/` 模块树**；VM 里我们编出了 **156 个 `.ko`** 但没进包。
现在能启动是因为关键功能多为 `=y` 内建。
⚠️ 内核还开了 `CONFIG_MODULE_FORCE_LOAD=y`：**vermagic 不匹配也照样加载** → 不会报错，但可能静默出问题。

**为什么现在就要管**：Q3 若把 HID gadget 编成 `=m`，它进不了板子；UVC/新驱动同理。
**怎么查**：`./build.sh modules`（帮助里写作 `kernel-modules[:<dst dir>]`）的投递目标，
以及 `ubuntu/mk-rootfs-noble.sh` / `post-build.sh` 里有没有拷 `kernel/.../modules` 的步骤。
**判据**：搞清楚"加一个 `.ko` 到板上"的正规路径，或明确决定"所有关键功能一律 `=y`"（更省事）。

## Q8 网络：定成 **WiFi** 🔴（2026-10-16 拍板；网线降为"调试备胎"，不再作前置）

**为什么 WiFi 站得住**：它同样满足"带外"这个本质要求 —— 网络路径**不经过被控机**，
被控机关机、重装系统、没驱动，KVM 照样在线。有线和 WiFi 在这一点上等价，只是介质不同。
再加两条现实理由：① 板子要**贴着被控机放**（HDMI 线和 USB 线都不能长），路由器口未必够；
② JetKVM Mini W 已经证明"纯无线 KVM"是能做的产品形态。

**但这个决定换来一条新硬约束**：WiFi 一旦配错（SSID/密码/信道/信号），**就没有第二次机会**——
板子没屏幕、没键盘，你只能爬到桌子底下接 1500000 串口去救。
⇒ **必须先有一条不依赖网络的通道**：P1.5 的 **Type-C ACM 控制台**（Windows 上多出一个 COM 口）
或 COM14 调试串口。**P1.5 从"顺手做做"升级为"前置必须"**（见本节末）。

**为什么必须提前**：假源方案从 P3-B 档起就要"浏览器打开 `http://板子IP:8000`"，
没网就只能停在 A 档（本地自环），**"浏览器出画"这一半永远证不了**。
而且 `apt install ffmpeg / iw / fonts-dejavu-core`（P3 全都要）**也得先联网** —— 网络是网络层的第一块 domino。

### "用 WiFi 行不行"——顺手去查了 JetKVM 自己怎么做（2026-10-16，读 `jetkvm/kvm` 源码）

**结论：原版 JetKVM 是纯有线，WiFi 和蓝牙都不用。** 三条硬证据：

| 证据 | 出处 |
|---|---|
| `const NetIfName = "eth0"` —— 网络接口名**写死成 eth0** | `network.go` |
| JSONRPC `getDeviceCapabilities` 返回的能力列表里**没有 `"wifi"`**；UI 的 `{hasWifi && <WifiNetworksCard/>}` 因此在原版上不渲染 | `jsonrpc.go:430` 附近、`ui/src/routes/devices.$id.settings.network.tsx:101,418` |
| 全仓库 `git grep -i "bluetooth\|\bble\b"` **0 命中** → 配网不靠蓝牙 | 同上（633 个文件） |

- 网络栈本身是自己实现的：NetworkManager D-Bus 瘦客户端 `pkg/nmlite` + 自带 DHCP 客户端 `pkg/nmlite/jetdhcpc`，
  还带 **mDNS**、**Tailscale**（能力列表里都有）。→ JetKVM 的"出门在外"是靠 **Tailscale**，不是靠 WiFi。
- ✅ **上一轮的"推理"现已证实**（读 2026-10-16 官方公告原文，非二手）：WiFi 那套 UI 就是给 **JetKVM Mini** 用的，
  公告原话 "**the same web interface** and the cloud **carry over unchanged**" → 同一份前端靠 `capabilities` 门控两种型号。
- 🔴 **但"Mini 用 WiFi+蓝牙"这个说法要改准**（公告原话逐条）：

  | | 型号与网口 | 无线 | 蓝牙干什么 |
  |---|---|---|---|
  | **Mini** | **$39，有 RJ45**（"has an RJ45 port"）| 无 | — |
  | **Mini W** | **$42，砍掉 RJ45** 换 2.4/5GHz 电台 | **ESP32-C5**：802.11a/b/g/n/ac/ax，2.4+5GHz，另有 802.15.4(Zigbee/Thread) | "**Setup happens over Bluetooth** from a browser on your phone or laptop: pick a network, enter the password" → **只做首配，不传数据** |

  ⇒ 也就是说 JetKVM 产品线的**基础款仍是有线**，WiFi 是给"线够不着的机器"准备的补充款，BLE 只做配网。
  ⚠️ **这跟我们的选择不矛盾**：JetKVM 出厂就带 RJ45 是它产品定义的一部分（机柜场景）；
  我们这台 K11C 是**贴着被控机放**、路由器口不一定够，所以**反过来选 WiFi**，把网线留作调试备胎。
  这条对照的价值在于：**JetKVM 用事实证明了 WiFi 路线能做产品，但也证明了它认为有线更可靠** —— 所以我们把 Q8.1–Q8.5 逐条写死。
- ⏳ **Mini 固件仓库现在还没开**：设备 **2026-10-26 上市**，公告写 "We rewrote the firmware for the ESP32-P4X,
  and **it will be open source from day one**" → 大概率 10-26 才出现在 org 里。
  已核实 org 现有 9 个仓库（`kvm`/`cloud-api`/`docs`/`rv1106-system`/`jetkvm-native`(archived)/
  `atx-extension-firmware`/`dc-extension-firmware`/`rkcrypto`/`engineering-job-challenge`），
  **没有 Mini 固件**；`jetkvm/docs` 仓库里 `git grep -i "jetkvm mini"` **0 命中**；
  猜的三个仓库名 `jetkvm/mini-firmware`、`jetkvm/esp32-p4-firmware`、`jetkvm/jetkvm-mini` 全部 **404**。
  → **想看 Mini 怎么实现 WiFi/BLE 配网，得等 10 天。**

BLE 配网 JetKVM Mini W 用了，但**那是裸机 MCU 没有串口才需要的**，我们有 UART + USB，不需要这层复杂度。

### 安全网（**因为选了 WiFi，这条从"顺手"变成"必须"**）：ACM gadget = 不依赖网络也能进板子

JetKVM 内置了 CDC-ACM gadget（`cdc_acm_console.go`，读写 `/dev/ttyGS0`，再用 WebRTC datachannel 转给浏览器）。
**我们内核已经是 `CONFIG_USB_CONFIGFS_ACM=y`**（Q3 那段已证）→
**不用重编内核**就能 configfs 建一个 ACM 功能：Type-C 插 Windows 会多出一个 COM 口。

一箭三雕，而且比网线还便宜：
1. 🔴 **它是 WiFi 路线的救命通道**：SSID 配错、路由器改了密码、DHCP 抽风 —— 只要 Type-C 还插着，
   就能从那个 COM 口进去修，**不用爬桌子底下接串口、也不用显示器**；
2. **它是 Q2 的最佳探针**：Windows 能枚举出 COM 口 = **device 角色实锤**，零重编、零硬件；
3. 调试不再受"COM14 被 MobaXterm 占着 / 1500000 串口丢帧"这套罪。

**排期上它是 Q8 的前置**：先做 P1.5（ACM），再动 P2.5（配 WiFi）。顺序反了就会很难受。

## Q9 供电形态 🟡（设计题，别漏）

做 device 接被控机时，USB 规范上 device 应受电于 host；但被控机可能限流，
而 KVM 必须 24 小时在线。→ **板子必须自己独立供电**（原装电源），Type-C 口只走数据。
**要顺手确认**：GND 共地、别出现"板子电源 + 被控机 USB"两头都灌电的回路（这也是 Q2 的一部分）。
P2 插线时就能验：摸板子有没有异常发热、`dmesg` 有没有 over-current。

## Q10 被控机认不认我们的 HID（**绝对坐标**是关键）🟡

**已知的坑**：只做相对鼠标，远程操作会漂到没法用。
→ HID report descriptor 要含**绝对坐标指针**（`Usage (Pointer)` + `Absolute`）。
**判据**：笔记本浏览器里点哪儿光标就去哪儿、不累积漂移（将来上手机同样成立）。
⚠️ **为什么一定要绝对坐标**：浏览器里我们已知指针的归一化坐标（0–32767），
直接映射到屏幕就是**零状态、零漂移**；相对模式要板子自己维护"当前光标在哪"，
被控机改速度/改分辨率/被别的鼠标动一下（**你这台笔记本自己的触控板就是第二个鼠标！**）就永久错位。
⚪ "能不能进 BIOS"这半已失去意义（档 2 下看不见），但绝对坐标这条**不因任何决定而放松**。

## Q11 GPL-2.0 边界 🟢

`jetkvm/kvm` 与 `cloud-api` 是 **GPL-2.0**，PiKVM 是 **GPL-3.0**。
**规则**：只看它的设计/接口自己写 → 不传染；复制改造它的代码 → 衍生品同样要开源。
自建路线（§3.2 路线 C）本来就打算"看它怎么分层，自己写零件"，注意**别整段抄源码**就干净。

## Q12 HDMI 出图 🔄（C5 改口：前期不接，**以后要接显示器**）

`card0-HDMI-A-1/status = disconnected` —— 因为没插显示器，**不是坏**（驱动 `dwhdmi` 已认出 HDMI 2.0 TX）。

⚠️ **接上显示器会看到什么，先把话说死**：HDMI out 是**板子自己的输出**，
它显示的是**板子自己渲染的东西**（假源那张图、板子的桌面、某个全屏播放器），
**不会自动变成被控机的画面** —— 因为被控机的画面现在压根不在板子里（走的是软件推屏，且已挂起）。

将来真想在显示器上看被控机画面，有两条路，都不便宜：
| 路 | 做法 | 代价 |
|---|---|---|
| ① 本地渲染收到的流 | 板子把 agent/采集来的流解码后用 DRM/KMS 全屏画出来 | 要写渲染管线 + 吃 CPU/硬编（Q6 那条 MPP 通道又变成前提）；**延迟还会多一段** |
| ② 显示器上跑浏览器 | 给显示器接个小主机/电视自带浏览器，打开板子那个网页 | 零开发量，但那就不是"板子输出"了 |

**现阶段结论**：HDMI out **不接**，只当"板子健康"的免费证据；哪天要接，先回来读这一节。

## Q13 ⏸**挂起**（P5 之后才相关）档 2 的三条运行前提（不做就"瞎"）

画面来自被控机里的 agent ⇒ **被控机一睡、agent 一挂，这台设备就同时失去眼睛和手的意义**（HID 还在，但你不知道按到哪）。

| 前提 | 具体要做什么 | 判据 |
|---|---|---|
| **永不休眠** | 被控机：电源计划"从不睡眠"、硬盘不休眠、**关屏可以但别断显卡输出**（很多截屏 API 在显示器断电时返回黑帧 → 要验） | 挂机一夜，早上画面还在 |
| **agent 开机自启 + 断线重连** | Windows 服务或计划任务（用户登录即起）；崩了要能被拉起来；被控机重启后**无人干预**能回来 | 手动 kill agent / 重启被控机，**60 秒内**画面自动回来 |
| **被控机 IP 可寻** | 路由器给被控机也按 MAC 绑 IP（和 Q8.4 同一件事，做两次）；或让 agent 反向连板子（**推荐**：板子 IP 固定，被控机主动来连，被控机 IP 变了也无所谓） | 被控机换网/重连后仍能连上 |

> 💡 **顺手解决第三条**：让 **agent 主动连板子**（板子开一个监听端口），而不是板子去连 agent。
> 这样只需要固定住**板子**的地址，被控机 DHCP 怎么变都不影响 —— 也顺便避开被控机防火墙入站规则。

## Q14 画面要不要过板子（P5 前定死）🟡

| 方案 | 好处 | 坏处 |
|---|---|---|
| **A 过板子**（推荐） | 浏览器/手机**只记一个地址**；被控机不用对外开端口（agent 反向连板子）；板子可以顺手录像存档 | 多一跳；板子要做转发（**只转发不重编，负载几乎为零**） |
| B 浏览器直连被控机 agent | 少一跳、延迟最低 | 画面和控制分散在两个地址、两台机器都要开入站端口、手机要连两个地方 —— **体验明显变差** |

⇒ **建议 A**：拓扑上板子永远是"唯一的门"，这也让后面加 Tailscale / 鉴权 / 录像都只改一处。
⚠️ 未证：转发会不会给 4×A55 带来意外开销（几十 Mbps 的 memcpy，理论上无压力）→ P5 实测记 CPU%。

## Q15 ⏸**挂起**（B3：现阶段不在被控机上装任何东西）被控机那个 agent 谁写、用什么 🟠

**这是"不买采集棒"换来的新成本**：本来 30 块钱硬件解决的事，现在变成一个要长期跑在被控机上的软件。

**它要干的活（最小集）**：截屏 → 编码 → 推到板子 → **崩了能自己起来** → **帧头带生成时间戳**。

| 环节 | 选项 | 备注 |
|---|---|---|
| 截屏 | Windows **DXGI Desktop Duplication**（`IDXGIOutputDuplication`） | 这是"能上生产"的那条路，快、支持 60fps。⚠️ **未证**：无显示器时是否返回黑帧（→ Q16）；换分辨率/锁屏/UAC 安全桌面会断流，要处理 |
| | GDI `BitBlt`（`PrintWindow`/桌面 DC） | 简单但慢（1080p 软采 ~15–20fps 量级），只适合当第一版验证 |
| 编码 | **硬件**：NVENC / AMF / QuickSync；**软件**：x264 `ultrafast zerolatency`、OpenH264、或 JPEG | 被控机是普通 PC 的话，硬编几乎白送；软编 1080p30 也扛得住（比板子强得多） |
| 传输 | 自己写：TCP/WebSocket 推 JPEG 或 H.264 裸流；或 **WebRTC**（复用现成库） | 目标形态是"浏览器一个地址看画面+操作"，所以**过板子中转**（Q14）时协议要自己定 |
| 自启 | Windows **服务**（Session 0 看不到桌面！）或 **计划任务-用户登录时** | 🔴 坑：截屏必须在**用户会话**里跑，做成 Service 会截到黑屏 → 用"登录时启动 + 崩溃自动重启"而不是服务 |
| 时间戳 | 帧头带**生成时刻**（建议单调时钟 + 两端各测一次 offset） | 见 §2-Q4 那条"时钟不同步 ⇒ 延迟是假的" |

**先别自己写的退路**：P5 第一版可以直接用 **Sunshine（host 端）** 或 RustDesk 拉流当替身，
先把"板子转发 + 浏览器出画 + HID 回环"跑通，再换成自己的 agent（**但现成方案给不了带时间戳的帧**，
所以延迟测量要么回到拍屏法，要么等自研）。
**判据**：被控机重启后 **60 秒内**画面自动回来（= Q13 一起验收）。
**许可证**：Sunshine 是 GPLv3、RustDesk AGPLv3 —— **只当外部替身用可以，别把它们的代码抄进我们自己的 agent**（Q11）。

## Q16 ⚪**已关闭**（被控机是笔记本、自带屏幕 ⇒ 风险不存在）被控机不接显示器会不会截到黑帧

**为什么要单列**：这是"画面来自被控机内部"这条路线**独有的新风险**，硬件采集路线不存在它。
GPU 在某个输出口没接显示器（或显示器断电）时，可能**不再渲染该输出**，截屏 API 就会拿到黑帧或零尺寸。

**先判断我们属不属于这个场景**：
- 被控机**平时就插着显示器/电视** ⇒ 基本不用担心，这条直接划掉；
- 想让被控机 **headless**（不接屏）跑 ⇒ 大概率会撞上。

**怎么验（5 分钟，P5 第一件事）**：把被控机显示器线拔掉 → 远程连进去看画面是不是黑的；
再插回去对比。⚠️ 未证：这台机器的显卡/驱动具体行为。
**解法（按省事排序）**：① 继续插着显示器（最省事）；② **HDMI 诱骗头 / EDID 假负载**（10–20 元，
⚠️ **注意这不是采集棒**，它不传输任何信号，只是骗 GPU"有屏幕"）；③ 虚拟显示器驱动（软件方案，驱动签名麻烦）。

## Q17 ⚪**已关闭**（C4：你选"不管安全"）谁能操作这台设备 —— 内容留作将来启用的清单 🟠

**问题**：定稿之后，板子在局域网里开着两样东西 —— 一个能出画面的 HTTP 端口，
和一条**能替你敲键盘的 USB 线**。同网段里任何人（或访客 WiFi、IoT 设备）都可能拿到那个页面，
**等于拿到你电脑的键盘鼠标**。这是这台设备区别于"一个摄像头"的地方，不能不设防。

**JetKVM 的参照**（读源码看到的开关，别照抄代码，照抄思路）：`tls`、`local_loopback`（只允许本机访问）、
`OIDC 登录`、Tailscale 组网。

**我们的最小方案（按省事排序，别一上来做全套）**：
1. **只绑 127.0.0.1 或指定网卡**，不 `0.0.0.0` 裸奔；
2. 一个**本地口令**（登录页 + 服务端校验，别只藏前端）；
3. 要出门再上 **Tailscale**（等于把设备从公网上"藏"进自己的 tailnet，省掉 TLS/端口转发）；
4. 控制页对"键盘事件"做**速率限制 + 明显 UI 状态**（正在被远程控制的提示），防止误操作。
**判据**：换一个没登录的设备打开那个地址，**看不到画面也发不出键鼠**。
⏱ 归属：**P4 做控制页时就要带上（第 1、2 条）**，别等 P6 再补 —— 补安全比补功能痛得多。
## Q18 🆕 移植清单：照 JetKVM 抄哪些文件（C2/C6 你选了"照它实现"）

**已读 `jetkvm/kvm` 源码**（`git clone --depth 1 --filter=blob:none`，633 个文件），下面全是**文件级**结论。

### A. HID 层：它的 configfs 布局（**这就是我们 P1/P2 要抄的东西**）

一个 composite gadget 上挂了 **4 个 HID 功能 + 1 个 ACM**，每个都是一个 `functions/hid.usbN` 目录：

| 功能 | `device` | order | protocol / subclass | report_length | no_out_endpoint | wakeup_on_write | 用途 |
|---|---|---|---|---|---|---|---|
| 键盘 | `hid.usb0` | 1000 | **1 / 1**（boot keyboard） | **8** | 0 | 0 | 标准 8 字节 HID 键盘报文 |
| 绝对坐标鼠标 | `hid.usb1` | 1001 | **2 / 0** | **6** | 1 | 0 | report descriptor 用 **Report ID 1 = 绝对 Pointer**（`Usage(Mouse)`→`Usage(Pointer)`+`Absolute`），同一功能里还带相对报告 |
| 相对坐标鼠标 | `hid.usb2` | 1002 | 2 / 0 | — | — | — | 兜底/兼容 |
| 唤醒设备 | `hid.usb3` | 1003 | **0 / 0** | **1** | 1 | **1** | vendor-defined（`Usage Page 0xff00`）只 1 字节，**专门用来远程唤醒被控机** |
| 串口控制台 | `acm.usb0` | 4000 | — | — | — | — | **就是我们 P1.5 想要的那个 COM 口**（`/dev/ttyGS0`） |

其它：`strings/0x409` 里 `product = "JetKVM USB Emulation Device"`（我们换成自己的名字）；
它还挂了 `uac1.usb0`（音频）和 `mass_storage.usb0`（虚拟光驱）——**我们现阶段都不做**。

源码位置（照这三个文件抄描述符最省事）：
`internal/usbgadget/hid_keyboard.go`、`hid_mouse_absolute.go`、`hid_mouse_relative.go`，
布局与属性写在各自的 `gadgetConfigItem{ path: []string{"functions","hid.usbN"}, attrs: {...}, reportDesc: ... }` 里；
键盘描述符注释标明**来源是内核文档 `Documentation/usb/gadget_hid.txt`**（那份文档本身是内核的，不算抄 JetKVM）。

### B. 移植到 RK3566 必须改的地方（**这几处是它的 RV1106 假设**）

| JetKVM 里的写法 | 我们这边 | 说明 |
|---|---|---|
| `getUdcs()` 读 **`/sys/devices/platform/usbdrd`** 下以 `.usb` 结尾的目录 | RK3566 是 **`/sys/devices/platform/fcc00000.usb`** | 🔴 路径不同，**直接抄会找不到 UDC** |
| `dwc3Path = /sys/bus/platform/drivers/dwc3`（unbind/bind 重绑） | **同名可用** | 重绑/复位这条路径我们一样能用 |
| `udcClassPath = /sys/class/udc`、`soft_connect` 节点 | **同名可用** | `soft_connect` 可以做"拔插模拟"，改 descriptor 时很有用 |
| 注释里写"**RV1106 的 DWC3 有个 race**：快速 unbind→bind 会让 `/dev/hidg0` 永久返回 ENXIO"，它的处理是**写一次探测 + 再重绑一次 + 睡 100ms** | ⚠️ **未证 RK3566 是否同样有** | 但**照抄这个防御逻辑没有坏处** —— 这类"字符设备存在但一写就 ENXIO"的坑，撞上一次能浪费半天 |
| `hidWriteTimeout = 100ms`（注释：留 10ms 会在正常连发时丢报文） | 直接沿用 | 我们写 HID 报文时也要有这个余量 |
| 健康检查用 `/dev/hidg0` 能否读写 | 沿用 | 判据现成 |

### C. 前端（C2：浏览器为主 + 照它移植）

- `ui/` 是 **React 19 + Vite + TypeScript**（`ui/package.json` 里 `name: "kvm-ui"`），路由是文件式（`ui/src/routes/devices.$id.settings.network.tsx` 这种）。
- 它和设备的通信是**两条通道**：`getNetworkSettings`/`getDeviceCapabilities` 这类**都走同一个 JSON-RPC**（`jsonrpc.go`，`writeJSONRPCEvent` 推事件），画面/音频走 **WebRTC datachannel**（`cdc_acm_console.go` 就是把 `/dev/ttyGS0` 和一个 datachannel 双向拷贝）。
- ⚠️ **移植前要先想清楚的一件事**：它的 UI 绑的是**它自己的 JSON-RPC 方法名和事件格式**。
  我们要"照它实现"，最省力的路线是 **连这套 RPC 协议一起实现**（前端几乎不用改），
  而不是自己定一套接口再改前端 —— 后者工作量更大还享受不到它的更新。
  **这一条是 P4 的第一个决定，等 P2 过了再定，我先记在这儿。**
- 许可证提醒（对应上半部分 §GPL）：抄 `ui/` 的代码 = 衍生品按 **GPL-2.0**；自用不分发没有义务，**要公开就得一起开源**。

### D. 我们**不抄**的部分

`pkg/nmlite`（它自己实现的 NetworkManager 客户端 + DHCP 客户端）—— **原版是纯有线 eth0，没有 WiFi**，
我们走 WiFi，直接用 Ubuntu 24.04 自带的 `NetworkManager`/`systemd-networkd` 就行，抄它等于自找麻烦。
`rv1106-system`、`mass_storage`、`uac1`、`cloud-api`、`atx/dc-extension` 全部不碰。

# 五、实施：假源方案与排期

## 5.0 假源方案：一张图 + 图上的毫秒表（不接采集棒、不接显示器；和被控机只有一根 USB）

### 先堵掉一个会白花钱的歧义

"让 HDMI out 默认输出一个图片"有两种理解，**第二种是死路**：

| | 说法 | 成不成立 |
|---|---|---|
| ❌ | 把 **HDMI out 用线绕回板子自己**当输入 | **不成立**。板子没有 HDMI 输入（§2-Q4 已证：`hdmi@fe0a0000` 是 TX，DTS 里无 hdmirx 节点）—— 绕回来的电信号没人接，跟用哪根线无关 |
| ✅ | **完全不碰 HDMI 电气层**：要的画面取**渲染前内存里的那一份帧**，直接喂编码器 | **成立**。而且**这正是最终形态的做法** —— 定档 2 之后，"在内存里截一帧"这件事从板子挪到了被控机的 agent 里，原理一模一样 |

按第二种理解，你要的就是：**板子自己有一张图 → 喂进编码 → 推给浏览器**，
不需要显示器、不需要采集棒（**本来就不需要**，见 §2-Q4 定稿）、做"画面"这半也不需要被控机
（但 **HID 那半必须有被控机**，那是 P2，假不了）。

### 但纯静态图会吞掉延迟测量 —— 所以图上要烧一个实时毫秒表

画面不变 ⇒ 无法知道浏览器那帧是多久前生成的，**"链路通了"和"链路快"会被混成一件事**。
解法很轻：那张图每帧被覆写当前时间戳（`drawtext`）。仍然是"一张图"，却自带可测时间差。

### 这套假源能证什么 / 不能证什么（2026-10-16 按"定档 2"重写过）

先说清一件事：**定档 2 之后，假源和最终形态的差别只剩"画面是谁的"** ——
两者都是**在内存里拿帧**（假源是自制图，最终是被控机 agent 截的桌面），**都不碰 HDMI、都不需要采集棒**。
所以这条测试**不是在演**，它测的就是最后真正会走的那条路。

| 能证（零成本） | **不能**证（别自欺） |
|---|---|
| 收流 → 转发 → 浏览器出画 整条软件通路 | **真实桌面的画面复杂度**：假源是静态图，编码几乎不花钱；真桌面一动就是全屏变化 → **码率瞬间飙升**，WiFi 与浏览器解码才是真正的考验 |
| **端到端延迟数字**（拍屏对比图上的毫秒表） | 被控机侧供电/枚举（Q9）—— 这条要靠 P2 插线 |
| 浏览器事件 → HID 报文 → 真打进被控机（**这条需要 Windows 配合，假不了**） | 被控机 **agent 崩了/休眠了** 会怎样（Q13 的三条前提只能到 P5 才验） |
| 板子做**转发**时的 CPU/内存余量（这才是定档 2 后板子的真实负载） | ~~采集段延迟~~ —— **已不存在**，我们不采 HDMI |
| 一个地址能不能同时给画面和控制页（Q14 的"过板子"方案） | 手机浏览器的触摸体验（要真机上手才知道划着别不别扭） |

> ⚠️ **定档 2 之后，"软编够不够"这个问题从主线上退场了**：编码搬到被控机（x86，强得多），板子只转发。
> 但它**没有完全作废** —— 只要将来想让板子做**录像存档 / 给手机降码率 / 多路复用**，就得板子自己编，
> 那时 RK MPP 硬编这条通道**仍然是前提**，而它**可能正是 `rockchip.service` failed（Q6）弄坏的**。
> 所以 P3-A 顺手查 `/dev/mpp_service` 这件事**保留**，只是从"决定成败"降级为"提前排雷"。

### 5.3.1 源：一张图 + 每帧覆写毫秒表


### 🔴 踩到并已定位的四个坑（每一个都能白耗半天）

1. **沿用官方 `VID_2207&PID_0006` 会让 HID 接口"消失"** —— Windows 装过的 Android 驱动按**硬件 ID** 把复合设备的**父节点整台认领**（设备节点连 `MI_` 都不生成），其它接口根本不拆开枚举。
   ⇒ 必须用**自己的 VID/PID**（我们先用 `1d6b:0104`，正式建议申请/挑一个不撞的）+ `bDeviceClass=EF/02/01`。
   排查特征：`Get-PnpDevice` 里只看到 `AndroidUsbDeviceClass`，**没有任何 `MI_xx` 子设备**。
2. **gadget 已绑 UDC 时，`ln -s function config` 会被 configfs 拒（EBUSY）** —— 而我第一版脚本把 `ln -s` 后面接了 `|| true`，**报错被吞掉**，于是"六个 function 都建好了、config 里却只有 adb"。
   ⇒ 正确顺序：**解绑 → 建 function + 链进 config → 再绑**；并且**永远别吞 `ln -s` 的错误**。
3. **这个 6.1 内核的 hid function 没有 `wakeup_on_write`**（那是 JetKVM 5.10 的厂改属性）→ 写它直接 `Permission denied`。远程唤醒暂时做不了，不影响键鼠。
4. **换 gadget 会杀死 adb，而 adbd 一死会把它派生的脚本一起带走** —— `setsid nohup` 也没扛住。
   ⇒ 用 **`systemd-run --collect`** 丢给 PID1 跑；或者干脆用串口/COM15。

1. 这颗 RK3566 的 dwc3 **没有** `/sys/class/udc/fcc00000.usb/mac_address`（`No such file or directory`）；
2. 脚本写的是 `cat mac_address 2>/dev/null | tr -d ':.\n-' > serialnumber || echo 00000001 > serialnumber` ——
   **管道的退出码是 `tr` 的 0，`||` 兜底永远不触发**，于是兜底形同不存在，写进去的就是空串。

对比：§5.4 上面那次**通过**的基线用的是 `k11c_min.sh`，serial 写死 `00000001`。
⇒ repo 里 `26_k11c_kvm/gadget/k11c-gadget.sh` 已改成 `SER=…`（先 mac_address，再退到网卡 MAC，再退到 `00000001`）。
板上已用 configfs 临时补成 `00000001` 并重绑生效，**但这是内存里的，重启就回到空**，要带上得下次烧写。

**🟡 已证 —— 一个会骗人的排查指标：`/sys/class/udc/*/state` 是粘的**

`echo '' > UDC` 解绑之后它仍然读 `addressed`，**不回到 `not attached`**。
所以 `state≠configured` **不能反推**"主机在试着枚举但失败了"；本轮 `addressed` 就是 21:52 烧写会话留下的残值。
判"对面到底有没有主机"要靠：`dmesg` 里**连续**多轮 `device reset`（主机三次重试的节奏约 0.67s）、
`/sys/class/extcon/extcon0/state`、以及 Windows 侧 PnP 有没有变化。
