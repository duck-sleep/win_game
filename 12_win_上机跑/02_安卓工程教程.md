# 安卓工程教程 — 给 Linux 背景工程师的 AOSP 上手指南

> 写给从 Linux 转过来的你：不讲 Java 语法，只讲**工程结构和运行机制**，全部对着本机 `10_code/` 真实代码讲。
> 配套文档：工程是什么看 `01_工程说明.md`；怎么编译看 `04_快速编译指令.md`。

## 一、心智模型：AOSP ≈ 自己动手攒一个 Linux 发行版

| Linux 世界 | Android 世界 | 对应本工程 |
|-----------|-------------|-----------|
| 内核源码 linux.git | GKI 内核 | `LA.VENDOR.15.4.3/kernel_platform/`（6.1） |
| glibc / musl | bionic libc | 各仓库 `bionic/` |
| systemd | init + init.rc 语言 | `system/core/rootdir/init*.rc` |
| 发行版包（coreutils 等） | 系统组件 APK/JAR | `frameworks/`、`packages/`、`system/` |
| 驱动 + 固件 | HAL + vendor 分区 | `vendor/qcom/`、`modem.zip` 里的固件 |
| grub / u-boot | bootloader（abl/UEFI） | modem 仓里的 uefi.elf |
| `make` + config | Soong/Android.bp + lunch | 各仓库 `build/` + `SNM970_A15_build.sh` |
| .deb/.rpm 包 | 分区镜像（.img） | out/ 里的 system.img、super.img |

**一个关键区别**：Linux 系统装在磁盘上是自由布局的目录树；Android 是**固定分区表**——每个分区装什么、由哪个仓库编出来，全是定死的（见第四节）。

## 二、三个仓库 = 一台手机的两个世界（Treble 分界）

Google 从 Android 8 起把系统劈成两半（Project Treble），QCOM 的发布也照此切仓库：

```
┌─────────────────────────────────────────────┐
│  LA.QSSI.15.0  —— "系统侧"（可换的安卓）        │
│  system / product / system_ext 分区           │
│  frameworks 框架、系统 App、Java 世界为主       │
│  ↑ 我们的游戏前端 ok-frontend.apk 也编在这       │
├────────── Treble 接口（HAL/manifest）─────────┤
│  LA.VENDOR.15.4.3 —— "厂商侧"（贴硬件的）       │
│  vendor / odm 分区 + 内核 + bootloader         │
│  device/qcom/kalama 设备配置、vendor/qcom HAL、 │
│  kernel_platform 内核、modem 固件集成           │
└─────────────────────────────────────────────┘
  qcm8550-modem_sign —— 预编译固件包（不解不编，解压集成）
```

**记住这个分界的实际意义**：
- 改 UI/App/框架 → 动 QSSI 仓库
- 改驱动/HAL/设备配置/内核 → 动 VENDOR 仓库
- 两侧只能通过 HAL 接口（`.hal` 文件、`manifest.xml` 声明）通信，不能直接互相 include 代码

## 三、顶层目录速查（对着 VENDOR 仓库 `ls` 讲）

| 目录 | 是什么 | 你会用到吗 |
|------|--------|-----------|
| `frameworks/` | Android 框架本体（AMS/WMS/View 系统），base 是核心 | 常用（QSSI 侧） |
| `packages/` | 系统 App：Settings、Launcher、SystemUI | 常用 |
| `system/` | 底层核心：init、bionic 相关、core（rootdir 里有全局 init.rc） | 常用 |
| `device/` | **设备定义**——一款板子一个目录：`device/qcom/kalama/` | **最常用**（第五节细讲） |
| `vendor/` | QCOM/厂商代码：HAL 实现、闭源二进制。VENDOR 仓里 `vendor/qcom/opensource/` 是 QCOM 开源 HAL | 常用 |
| `kernel_platform/` | 真内核（GKI + msm-kernel）。注意顶层还有个 `kernel/` 目录，**基本是空的**，别被骗 | 改驱动才用 |
| `hardware/` | Google 定义的硬件接口参考实现（如 keymaster） | 少用 |
| `external/` | 300+ 个第三方开源库（openssl、zlib……相当于发行版的依赖池） | 查问题用 |
| `prebuilts/` | 预编译工具链：gcc/clang/python/各种 host 工具 | 编译报错找不到工具时看它 |
| `build/` / `build.sh` | 构建系统本体（Soong 源码）+ QCOM 的构建入口 | 排查编译问题 |
| `bootable/` | recovery（A/B 设备已并入 boot） | 少用 |
| `art/` `libcore/` `libnativehelper/` | Java 运行时 ART / 核心类库 | 罕见 |
| `bionic/` | Android 的 libc | 罕见 |
| `cts/` `sdk/` `pdk/` `test/` | 测试套件/SDK | 不用 |
| `modem/` + `modem.zip` | 基带等预编译固件（VENDOR 仓独有，编译时解压） | 脚本自动处理 |
| `out/` | **编译产物**全在这，删掉重编不心疼（除了时间） | 常看 |

## 四、分区与镜像：编译到底编出了什么

刷机包里每个 img 对应一个分区，**哪个仓库编哪个**是固定的：

| 镜像 | 分区放什么 | 谁编的 |
|------|-----------|--------|
| `boot.img` | GKI 内核 + 通用 ramdisk | VENDOR（kernel 阶段） |
| `init_boot.img` | 通用 ramdisk（A15 独立出来了） | VENDOR |
| `vendor_boot.img` | vendor ramdisk（第一阶段的 rc/固件） | VENDOR |
| `dtbo.img` | 设备树覆盖（屏幕/按键/接口配置！） | VENDOR |
| `vbmeta.img` | AVB 校验元数据（验其他镜像签名） | 自动 |
| `super.img` | **动态分区容器**，内含下面四个 | 两仓库各编各的拼起来 |
| ├ `system.img` | 框架、系统 App | QSSI |
| ├ `product.img` | 产品定制 App/Overlay | QSSI |
| ├ `system_ext.img` | 系统扩展 | QSSI |
| └ `vendor.img` / `odm.img` | HAL、设备配置、固件 | VENDOR |

本工程最终产物（`vendor/vendorcode/build/`）：
- `SNM970_userdebug_01.zip` —— 刷机包
- `*_ota.zip` —— OTA 升级包
- `sparseimage/` —— fastboot 逐分区烧录镜像（救砖用）

## 五、device/qcom/kalama/ —— 设备定义（你的主战场）

这个目录定义"这台掌机是什么"，每个文件都值得认识：

| 文件 | 作用 | 类比 Linux |
|------|------|-----------|
| `BoardConfig.mk` | 板级硬配置：分区大小、架构、dtb、签名 | 内核 defconfig + 分区表 |
| `kalama.mk` | 设备 makefile：装哪些模块、哪些属性 | 发行版包清单 |
| `AndroidProducts.mk` | 声明产品名 → lunch 的 `kalama-userdebug` 从这来 | — |
| `init.target.rc` | 设备初始化（服务、属性、挂载） | systemd unit |
| `fstab.qcom` | 分区挂载表 | /etc/fstab |
| `system.prop` | 本设备系统属性默认值 | sysctl.conf |
| `gpio-keys.kl` | 按键→Linux code→Android 按键 映射（掌机按键！） | evdev 配置 |
| `firmware/` | 设备树 dtbo 相关固件 | dtb |
| `manifest_kalama.xml` | 本机提供哪些 HAL 服务 | systemd 服务声明 |
| `SNM970_gpio.sh` | 我们自己的 GPIO 初始化（定制） | 自启脚本 |

**修改生效规则**（重要）：
- 改 `*.rc` / `*.prop` / `BoardConfig` → 影响的是 vendor_boot/vendor 分区 → 必须重新编译打包刷机
- 改 `gpio-keys.kl` → 只是个配置文件，理论上可 `adb push` 到 `/system/usr/keylayout/` 热试

## 六、属性系统 = Android 的"动态配置总线"

init.rc 用属性触发动作（类比 systemd 的 Condition + systemctl set-property）：

```bash
adb shell getprop sys.usb.config        # 读
adb shell setprop sys.usb.config mtp    # 写（临时，重启失效）
adb shell getprop | grep usb            # 全量过滤
```

**前缀决定语义**（排查问题必背）：

| 前缀 | 存哪 | 特点 |
|------|------|------|
| `ro.*` | 内存 | 只读，编译期定死（build.prop） |
| `persist.*` | `/data/property/` | 跨重启保留 —— **改默认行为改这个** |
| `sys.*` | 内存 | 运行时状态，init 监听它切 USB 功能 |
| `vendor.*` | — | vendor 分区专用命名空间 |
| `init.svc.*` | 自动 | 服务状态（running/stopped），≈ systemctl status |

属性定义的位置：`device/**/system.prop`、`*.mk` 里的 `PRODUCT_PROPERTY_OVERRIDES`，编译时打进对应分区的 `build.prop`。

## 七、构建系统三层结构（30 秒版）

```
Android.bp ──→ Soong（真正的构建器）
Android.mk ──→ kati（转成 ninja）
                ↓
           out/combined-*.ninja ──→ ninja 执行编译
```

- **Android.bp 是未来**（Soong，Go 写的）；Android.mk 是历史包袱，两者混存
- `source build/envsetup.sh` 后才有 `lunch`/`mm`/`m` 命令
- `lunch kalama-userdebug` = 选产品，决定用哪个 device 目录、编哪些模块
- `out/` 里 `soong.log`、`verbose.log` 是排查编译错误的第一现场
- 全量编译由 `SNM970_A15_build.sh` 驱动（QSSI → 内核 → Target → 打包），**日常不要手动 lunch 全量编**（旧环境踩过污染的坑）

**单编 + 快速验证循环**（改 App/框架最常用，几分钟代替几小时）：

```bash
cd LA.VENDOR.15.4.3 && source build/envsetup.sh && lunch kalama-userdebug
# 改完某个模块代码后，在模块目录：
mm                                  # 只编当前模块
adb root && adb remount             # userdebug 特权
adb sync                            # 推送变更到设备对应分区
# 或者 APK 类的直接：
adb install -r out/.../xxx.apk
```

## 八、HAL 一句话 + SEPolicy 一句话

**HAL**：vendor 侧跑一个 native 服务（如 `android.hardware.usb@1.2-service-qti`），框架通过 binder 调它；设备 `manifest_kalama.xml` 里声明"我提供哪些 HAL"。找硬件问题 = 找对应 HAL 服务 → `ps -A | grep hardware`。

**SEPolicy**：一切进程对一切资源的访问都要策略允许。出问题时先看 `adb shell dmesg | grep avc` 或 `logcat | grep avc: denied`，报哪个 `scontext` 访问哪个 `tcontext`，去 `device/qcom/sepolicy_vndr` 或 `vendor/qcom/` 的 `.te` 文件加规则。规则：**先看拒绝日志，再写规则，别瞎猜**。

## 九、找代码的姿势

```bash
# 按属性找定义（比如想知道 sys.usb.config 谁在用）
grep -rn "sys.usb.config" --include="*.rc" --include="*.java" 目录/

# 找某个 App/服务装到哪
grep -rn "LOCAL_PACKAGE_NAME\|name:" packages/目标/Android.bp

# 看一个 APK 是预装还是用户装的
adb shell pm list packages -f | grep 关键词

# 服务在跑吗（≡ systemctl）
adb shell ps -A | grep 服务名
adb shell getprop init.svc.服务名

# 日志分区看
adb logcat -s UsbDeviceManager:V    # 只看一个 tag
adb logcat *:E                       # 只看 error
```
