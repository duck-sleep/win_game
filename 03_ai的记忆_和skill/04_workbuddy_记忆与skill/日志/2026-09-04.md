## 根因重大修正：mono→DIRECT 直通、stereo→MIXER（AudioFlinger dump 铁证）

- 之前"BSP secondary outputs 失效"结论**需要修正为更精确的机制**：
- **MODE_STATIC + mono** 测试音 → track flags 0x200(FAST) → DIRECT 直通轨，无 secondary（测试方法缺陷）
- **MODE_STREAM + mono** 测试音 → track flags 0x000，但仍路由到 AudioOut_5D（DIRECT 线程，AudioStreamOut flags 0x1=DIRECT，device=SPEAKER），**因为 mono 流被高通 BSP 选 DIRECT 直通**
- 关键：AudioOut_D（primary MIXER）flags 0x6 = PRIMARY|FAST，跑 FastMixer；AudioOut_5D 是独立的 DIRECT 扬声器线程
- **只有 stereo 走 MIXER（AudioOut_D）才会触发播放采集的 secondary outputs（TeePatch 影子轨）**
- 之前 PPSSPP(OpenSL)/Music 采集不到，**尚未在 stereo MIXER 轨上验证**——之前测试音全是 mono 被 DIRECT 吃掉
- 已改 TonePlayer：MODE_STATIC→MODE_STREAM、mono→stereo（buf 2048，双声道正弦波），对齐真实游戏场景
- 待验证：stereo 测试音是否进 AudioOut_D(MIXER) + 影子轨激活 + 电平>0
- 若 stereo 仍采集不到 → 才回到 BSP 深挖（secondary outputs 在 FastMixer 场景下的激活）；若 stereo 能采到 → 结论是 mono 流的 DIRECT 直通问题，采集端应改 stereo 或强制 MIXER

## 根因彻底锁定 + 两阶段修复方向（干净环境 property 实验验证）

### 决定性结论（AudioFlinger dump 对拍 + property 实验）

**根因 A（主因）**：高通 BSP 的 `vendor.audio.offload.track.enable`（默认 true）在 APM `getOutputForAttr`（AudioPolicyManager.cpp ~1848-1857 行）强制把 `AUDIO_STREAM_MUSIC + USAGE_MEDIA/GAME` 的 PCM 流设成 `AUDIO_OUTPUT_FLAG_DIRECT`（PCM offload 直通），**绕过 MIXER**，导致播放采集的 secondary outputs 影子轨机制根本无从触发。
- 代码位置：`frameworks/av/services/audiopolicy/managerdefault/AudioPolicyManager.cpp` 内嵌高通私改，`trackDirectPCM = property_get_bool("vendor.audio.offload.track.enable", true)`
- 验证：`setprop vendor.audio.offload.track.enable false`（需 root）+ `killall audioserver` 后，测试音（440Hz stereo MODE_STREAM USAGE_MEDIA）从 DIRECT 线程（AudioOut_5D）回到 MIXER 线程

**根因 B（次因，offload=false 后暴露）**：offload=false 后 MEDIA 流被 `audio.deep_buffer.media`（默认 true）路由到 **DEEP_BUFFER 输出线程（AudioOut_25）**，但该线程在本板是**坏的**：`Blocked in write: yes`、`Frames written: 0`、`Timestamp rate=nan`（HAL 输出从未启动）。线程卡死 → threadLoop 不跑 → `updateTeePatches_l()` 不执行 → 影子轨（patchTrack）永远 IDLE 不被 start → REMOTE_SUBMIX 输出 Frames written 0 → 采集静音。
- 影子轨证据：AudioOut_5D(REMOTE_SUBMIX MIXER) 里 `P 65/P 62 ... I ... 0 active`（I=IDLE，从未 start）
- `audio.deep_buffer.media=false` 会导致采集端 `could not register audio policy`（破坏 REMOTE_SUBMIX policy 注册），此路不通

### 完整因果链
MEDIA/GAME 音频 → (offload=true)DIRECT 直通 / (offload=false)DEEP_BUFFER 坏线程 —— 两条路都到不了正常工作的 primary MIXER(AudioOut_D) → secondary outputs 影子轨要么不建、要么建了 IDLE → 播放采集永远静音

### 修复方向（需改 BSP 代码，非 property 可解）
让播放采集的 MEDIA/GAME 音频**绕过 offload 直通 + 不走 DEEP_BUFFER**，直接进 primary MIXER(AudioOut_D)。落点在 AudioPolicyManager.cpp 的高通私改段，加条件：当存在 loopback render policy mix（播放采集授权中）时，不强制 DIRECT、不强制 DEEP_BUFFER，让其走 primary MIXER。
- 即：`vendor.audio.offload.track.enable` 的强制 DIRECT 逻辑，需对"已注册 loopback 采集 mix"的场景豁免

## 自动 host 方案修正（11:55，用户决策：默认 device 保 adb）

- **原方案缺陷**：rc 用 `on property:sys.boot_completed=1` 开机强制 host，会导致单 USB 口（a600000，adb 与 OTG host 共用）开机即断 USB adb
- **用户决策**：默认 device（peripheral 保 adb），接手柄时手动切 host
- **最终 rc**（init.snm.usb.rc）：
  - `on boot`：setprop persist.vendor.snm.usb_host 0 + write mode peripheral（强制复位，防 persist 残留导致开机进 host）
  - `on property:persist.vendor.snm.usb_host=1`：write mode host
  - `on property:persist.vendor.snm.usb_host=0`：write mode peripheral
- **用法**：切 host 前先开 WiFi adb，`setprop persist.vendor.snm.usb_host 1`；用完 `setprop ... 0` 切回
- 关键事实：板子**只有一个 USB 控制器 a600000**（`/sys/class/udc/` 只有 a600000.dwc3），gadget=diag,adb，mode=peripheral；WiFi 当前 DISCONNECTED 无 IP，不能当默认调试通道
