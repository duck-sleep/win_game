做"与参考一致"类验收（diff 豁免、秘密扫描白名单等）时，按这套规矩，别用名单式/关键词式豁免：

1. **先消差异，再豁免**：能靠对齐条件消掉的差异先消（例：把重建树挪到与参考树完全相同的绝对路径再编一次），消不掉的单独报告原因。
2. **白名单写死三要素**：只认指定条目，每条 = 文件路径 + 行号 + 该行内容 sha256，三样全对上才放过；先验证参考侧同位置同内容存在；其余任何命中一律 FAIL。**不准按关键词、按目录整片忽略**。
3. **豁免走窄规则，不走文件名单**：规则具体到字节/字段级（例：pyc 只许头部 mtime 4 字节不同，magic/flags/源大小/正文必须相同；ELF 大小+每段大小相同、.text 逐字节相同、差异字节只落在日期/时间/git哈希格式串内）。脚本逐文件判它套哪条规则，**不准读证据文档/名单来豁免**。
4. **套不进任何规则 = FAIL**，不准临时加规则让它过；真要加规则，先停下来问用户。
5. **不准改参考树、不准改判据、不准为了过验收改源码或 patch 内容**。
6. 脚本末尾打印每条规则命中数 +「无法解释: N」，报告贴原始输出。交付：剩余差异文件数、每条规则命中数、最终验收输出。
7. **拍板后的执行次序写死**："先做能消掉的，再加规则；**加完之前不许报 PASS**"。用户会逐组指定"消/加规则"并给出消差异的精确做法与判据（如"逐字节相同，或只剩 X 差且大小/.text 相同"），照判据核验，对不上就停下贴剩余差异，不许自行豁免。加规则只许限定在用户批准的字节位置，**不写成"这几个文件可以不同"**。
8. 构建流程里为消差异加的步骤可以写进 README 构建节，但**验收标准/任务书口径一字不改**。

**Why:** 2026-11-20 BSP L2 验收，我提了"617 个文件按名单豁免"，用户否掉，改成上面这套（同路径重编 + 窄规则 + 写死白名单）；11-21 对剩余三组无法解释逐项拍板时又追加了第 7、8 条次序规矩（"先做能消掉的，再加规则。加完之前不许报 L2_PASS"）。名单/关键词式豁免会掩盖真实差异、不可审计；他要的是可复现、可核对、边界清晰的判定。

**How to apply:** 任何一致性验收、秘密扫描、diff 豁免场景都照此办理。证据文档可以留档给人看，但脚本判定必须独立按规则跑。给豁免选项时直接按"窄规则 + 先消差异"设计，别再提名单式方案。关联 [[feedback-plan-validation-mode]]、[[feedback-instrument-and-explain-metrics]]、[[k11c-bsp-split-line]]。
