**两条要一起遵守的规矩：**

**① 分清"验方案"和"干活"两种模式。** 用户明说过
「你先别干 我们验方案 干的时候我和你说」。验证期内**只读、只写文档、不动内核/板子/编译**；
可以给"下一步要不要我执行"的提议，但不能自己开干。

**Why:** 他要先在纸面上把架构和卡点吵透，才愿意投入机时和钱（这条线里"花钱"=买采集棒，"机时"=重编烧写）。
他和我的分工是：**他拍方向、我证可行性并主动找漏洞**——他自己会抛方案让我挑刺
（例："typec 是不是强制 device 就行了"），期望的答复是"对，但还有 3 个边界"，不是"好的我执行"。

**② 给人看的方案文档一律"先总后分"，并且诚实标注证据等级。**
原话：「你用先总后分的写一下 我看看问题在哪 我们挨个解决 对你不了解的地方 挨个解决」。
固定形态：结论/一句话 → **问题清单表（按"卡人程度"排序，带状态与归属阶段）** → 逐条展开 → 背景依据 → BOM → 排期。
每条必须写：**已证 / 未证**（未证的一律配"可执行的验证命令 + 判据"），
以及"万一不通的退路是什么"。他反复抓我这点，所以**不要把推测写成结论**。

**How to apply:**
- 每条硬件/内核结论都要给来源（dts 行号、DXF 网络名、板上实测、官方原话），并把"抽不出文字/没验"这类手段局限说清
- **方案一改就要自查有没有留下互相矛盾的老段落**（架构描述、旧排期表、"证明①②"这类老措辞）；
  他自己会指出（「目标架构这些还是老的」）。改完在文档里留一行"哪条是我自己排错并已改正的"，他不反感我认错，反感我藏着。
- 新方案会**暴露新的排期依赖**（例：假源要开浏览器 → 网络必须提前），要主动重排并说明为什么，而不是沿用旧序
- 涉及"能不能测到/能不能假掉"要诚实列**能证 vs 不能证**两栏，防止拿假源数字当产品指标

与 [[feedback-ai-executes-not-pastes]] 不冲突：那条说**执行期要自己跑完报结果**，
这条说**验证期不要抢跑**；判断依据是用户有没有给"干"的字。
