两条从 2026-10-18 定下来的做法：

**1. 现象可疑时先造可观测性，不要靠推理轮流转。**
用户报"手机页面 RPC 一直是 `-`，你认真看看"。我先后怀疑过缓存、JS 报错、手机网络，都没法定论；
最后给服务端加了一个 RPC 计数（`total` / `by_method` / `last_peer` / `last_err`，挂在 `/state` 上，不逐条刷日志），
一步就分清"手机根本没发请求"还是"发了但界面没显示"—— 结论是**两者都没坏**：那个字段只在有动作后才刷新，
而计数证明手机确实发了 1742 次、0 错误。

**2. 报任何数字都要同时说清"它量的是哪一段"和"它不包含什么"。**
他直接问"这个 rpc 和最快是什么意思"。有效的答法是：`上次 RPC` = 手机 fetch 出去到收到回包的往返（含 WiFi + HTTP + 写 HID），
`最快` = 本次开页面以来的最小值，用来对比出抖动；**它不包含画面延迟**（那是另一件事，要拍屏对码表量）。
顺带把服务端实测的 0.4ms 贴出来，他立刻就懂了自己看到的 50ms 是谁贡献的。

**3. 报"省了 X 毫秒 / 提升了 X 倍"之前，先确认那个基线是在什么状态下量的。**
2026-10-21：我把控制从 HTTP 搬到 WebRTC datachannel，自己机器上量到 `HTTP 53ms → DC 10ms`，就报告"省 43ms、5.3 倍"。
用户真机试完只回一句"**感觉体验不出来**"。查下来：那 53ms 是**内嵌浏览器处于隐藏页面**时量的，Chrome 会节流，
基线本身被抬高了 —— 收益是真的存在，但量级不能那么报。
同一台机器上"隐藏页面"这个状态**已经第三次**咬我：报假丢帧、事件不投递、HTTP 往返被抬高。
⇒ **凡是"我这边量的数"要和"他的体验"对比，先问：我的测量环境是不是和他那个不一样？能不能在他那边复测一次？**
不能复测就把话说成"我这边量到 X，他那边待测"，别直接报成收益。

**4. 同框对码表时，一定要先讲清"数字大 = 谁更慢"。**
2026-10-29：手机 `00:39:19.606`、电视 `00:39:19.639`，他第一反应是"**这两个延迟比较好低啊…为什么手机延迟还比 tv 低呢 这个很奇怪**"
—— 把"时间码更小"读成了"延迟更低"。正确的说法是把方向和物理一起吃给他：
**时间码小 = 那一帧更旧 = 手机比电视慢 33 ms（60fps 2 帧）**；而且屏幕端**不可能**快过直出端
（电视是同一块缓冲 DMA 扫出去，网络端还要叠 编码→传输→解码→浏览器合成）。
⇒ 报任何"A 比 B 快/慢"的读数，**第一句就把坐标系说清**（谁的数字大谁慢、差几帧），别只甩两个数。

**Why:** 他不是在质疑结论，而是**按数字做决策**的人 —— 数字口径不清或"看不出系统内部发生了什么"，就会反复来回问，
比修 bug 本身更耗时。

**How to apply:** 遇到"没反应/显示不对"，先问自己"我能不能 5 分钟内让它自己报告发生了什么"，能就先加，别猜第三轮。
给指标时一句话交代测量点、路径分段、以及不包含的部分。
另外：**有副作用的默认值要关着**（那次页面里"发送后回车"默认勾着，他反馈"这个可以不用也行"），
需要时让他手动开，不要替他多做动作。
