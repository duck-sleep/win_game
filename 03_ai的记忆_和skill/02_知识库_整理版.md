## 四、M.2 SSD 问题（当前主战场）

### 根因（硬件+软件双重）

1. **硬件**：J901 M.2 插座 PCIe 差分线交叉 → 板厂已跳线修正
2. **软件**：
   - GPIO46 供电使能脚（VCC5V_EN，R136 100K 默认拉低）**没驱动** → SSD 无电
   - `pcie1` 的 `boot-option` 非 0 → 不在开机时枚举

### 修复（已写入，等编译验证）

两个 overlay 文件都要改（**缺一不可**）：
- `kernel_platform/qcom/proprietary/devicetree/qcom/kalamap-hdk-overlay.dts`（主 overlay）
- `kernel_platform/qcom/proprietary/devicetree/qcom/kalamap-hdk-overlay-gpiotest.dts`（工厂测试 overlay）

每处加同样两块：
```dts
&tlmm {
        pcie_slot_3v3_en {
                gpio-hog; gpios = <46 0>; output-high;
                line-name = "pcie-slot-3v3-en";
        };
};
&pcie1 {
        qcom,boot-option = <0x0>;   /* 基础dtsi是0x1，hdk dtsi是0x2，我们覆盖成0x0=开机枚举 */
};
```

### 为什么 gpiotest 也必须改

- gpiotest overlay 声明了与主 overlay **相同的 board-id (0x1001f)**，仅用 `qcom,oem-id = <3>` 区分
- gpiotest 条目在 dtbo.img 里**排在主 overlay 前面**
- UEFI（LocateDeviceTree.c）按 msm-id → board-id → oem-id 匹配，**完全平局时按条目顺序选先出现的** → 正常开机也可能选中 gpiotest → 不改它，修复可能失效

### 验证 SSD（刷机后，Windows 有 adb）

```
adb shell ls /sys/block/              ← 看到 nvme0n1 即成功
adb shell su -c "dmesg | grep -i nvme"
```

## 五、设备树知识（从同事提交学到的规范）

### 同事改 dts 的两种方式

1. **新增 overlay 文件**（wanghao_sh 的 gpiotest，TaskID 86215）：新 dts + Makefile 注册 `.dtbo`
2. **直接改现有 overlay**（lijie 的 RS232/RS485，TaskID 87456）：`&qupv3_se6_4uart { qcom,rs485-en-gpio = <&tlmm 10 0x00>; };`

我们的 SSD 修改走方式二，与同事无节点冲突，不会冲突。

### dts 源码与编译路径关系

- 改动写在 `kernel_platform/qcom/proprietary/devicetree/qcom/`
- 编译实际读 `kernel_platform/msm-kernel/arch/arm64/boot/dts/vendor/qcom/`
- 两者内容**逐字节同步**（构建系统维护映射），diff 验证过为空
- 冒烟编译验证语法：用 prebuilts 的 clang-r450784e + build-tools 的 dtc 单独编 dts（命令存档在 `.dtbo.cmd` 文件里）

## 八、VM 环境经验（来自旧项目，仍适用）

- VM 内存 40-44G（宿主 64G）、6 vCPU（**别等于宿主逻辑核数，会调度死锁**）
- NAT 网络出外网；Windows FlClash TUN 负责境外流量
- VM 内**不能装** mihomo 或设 http_proxy 等代理变量
- systemd-oomd 必须 disable + mask（否则编译被杀）；tracker-miner-fs-3 也要 mask（偷 CPU）
- Ubuntu sudo 要密码 → 非交互 SSH 里执行不了 sudo，需用户手动
- SSH 公钥 ~/.ssh/authorized_keys 权限 600；API key 环境变量放 ~/.bash_profile
- 编译命令逐条粘贴（多条一起会串行粘连出错）
